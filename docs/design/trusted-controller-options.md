# 可信控制器的方案分析（task-007）

本文供用户选择架构方案，不是已批准的 ADR，也不表示任何方案已经通过隔离验收。
本轮只分析文档，没有执行 WSL、改权限、调用真实 Agent 或联网。

这里的“控制器”负责启动任务、保存证据和运行固定裁决规则；“裁判”是其中判断
诱饵测试结果的部分。“hub”是长期运行的编排程序，包括事件采集、状态流转和执行器。
控制器需要可信，不代表模型、模型输出或待审仓库也变成可信。

## 2. 威胁模型：具体防谁、保护什么

### 2.1 假设 Agent 已受提示注入影响

假设 Issue、仓库文件或工具结果能诱导 Agent 执行任意 worker 权限内的操作。
它可以改自己的工作仓库、运行命令、造 JSON、打印假错误、创建链接、启动后代进程，
也可以不执行探测，只声称“已经被挡住”。不依赖它遵守提示词。

要保护的是控制器的生效代码和策略、裁决记录、私人资料、合并权限凭据，
以及“只有证据充分才允许后台运行”的准入条件。具体攻击包括：

- 把裁判函数改成永远通过，等待管理员下一次执行这份仓库。
- 替换 `result.json`，伪造 UID、CLI 版本和 `blocked`，或重放上轮成功记录。
- 打印 `Permission denied` 和假 Git ref，让裁判误认真实操作被拒绝或通信成功。
- 读取 hub 的 GitHub token、进程环境或凭据缓存，借它推送、合并或篡改检查。
- 让输出文件名含 `../`，或在路径上放链接，诱导高权限控制器写到其他位置。
- 直接连接白名单外地址，或把秘密藏到未扫描的可写目录。

### 2.2 安全分析的前提和边界

信任用户批准的控制器版本、其安装过程和操作系统的权限机制；假设 worker
尚未取得 Linux root、控制器账户或 Windows 管理员权限。
本题优先防普通权限下的恶意 Agent，不承诺抵御内核、WSL 或虚拟化漏洞逃逸，
也不防已控制宿主的管理员、物理攻击或操作系统本身被攻破。
这些前提若不成立，A、B 的边界都要重新评估。

Agent 仍可能写出逻辑错误的产品代码，需要测试和审查；权限分离不能证明代码正确。
worker 使用的模型登录材料仍可能被该 worker 盗用，必须按泄漏风险限制权限和额度。
磁盘耗尽、无限输出和后代进程属于需要限额、超时及清理的故障/攻击面，
这里提出要求，不声称方案天然解决所有拒绝服务问题。

本次比较的主要攻击者是后台 WSL worker。
如果另一个前台 Agent 与控制器使用同一 Windows 账户且能任意改宿主文件，
那么仅限制 WSL worker 并不能保护控制器免受那个前台 Agent 攻击。
若也要防它，就要扩大威胁模型，并另设它无法访问的控制器身份或运行环境。

### 2.3 所有方案都要保留的三条约束

**裁判不能从待审仓库加载运行代码。** 不仅主脚本，Python 导入路径、虚拟环境、
依赖、插件、启动脚本和工作目录都要受保护。worker 可以提交候选修改，
但不能自行把它安装成正在生效的裁判或 `risk.yml`。
控制器升级应由用户审查并固定版本，不能自动执行 PR 带来的控制器代码或安装钩子。

**保存真实输出，不等于输出描述的事件真实。** 控制器直接收取 stdout/stderr，
只能证明“这个进程输出了这些字节”。哈希可以发现封存后的变化，
随机本轮标识可以防误用旧记录；它们都不能证明打印的系统调用真正发生过。
已知本轮标识的 Agent 仍能造事件，给自述签名也不能修复这个问题。

**准入必须区分未尝试、已拒绝、越界成功和无法取证。**
要判断拒绝，需要可信探测入口或权限层观察，把准确操作、目标、实际执行身份和结果绑定。
若固定探测只复用了 Linux UID，却绕过了 Agent 的工具沙箱，它最多验证账户权限，
不能拿来证明那一版 Agent 的沙箱生效。
坏事件、缺失身份或不完整扫描要保留为证据不足；原始流要完整检查泄漏，
不能把解析失败的行直接丢掉。

GitHub 仍是最终合并闸门：CI、审查和人工批准继续绑定待合并提交。
本地诱饵结果只是后台准入的证据，不能替代 CI，也不能授权绕过分支保护。

## 3. 方案 A：同一发行版内分成两个用户

### 3.1 信任边界

下面的 `controller`、`worker` 是两个不同的 Linux 账户；图中路径只是候选布局。
root 只承担受控的安装和身份切换，不让整个 Agent 进程以 root 运行。

```text
Windows host / trusted administrator
                  |
+-----------------v------------------------------------------+
| WSL: tandem                                                |
|                                                            |
| controller UID                                             |
| /opt/tandem-controller + private runtime + active policy    |
| private evidence + hub credentials                         |
|          |                                                 |
|          | fixed launcher + private capture pipe            |
| ========= Linux UID / filesystem / process boundary ====== |
|          v                                                 |
| worker UID                                                 |
| /home/worker/work + model login                             |
| Agent + editable repository + untrusted stdout/stderr      |
+------------------------------------------------------------+
```

这里真正承担保护的是 Linux 权限边界，不是目录名字。
控制器进程对 worker 切换身份的启动机制需要单独设计：例如由管理员安装固定的窄接口，
只允许启动约定的低权限任务，不能让 worker 借此选择任意用户或高权限命令。
普通 controller 账户并不天然有切换为其他 UID 的能力。

### 3.2 凭据由谁持有

| 主体 | 凭据和用途 | worker 的关系 |
|---|---|---|
| controller / hub | 事件采集所需的仓库读取凭据；确需写入时另列最小权限 | 不得通过文件、环境继承、共享缓存或进程访问取得 |
| worker | 仅任务必需的模型登录材料；默认不给仓库 token | 能读取自身凭据，故须接受其可能被盗用的风险 |
| 可选的代码提交接口 | 将经约束的成果送到候选分支所需的窄权限凭据 | 由可信侧持有；不提供任意 Git 命令代理 |
| GitHub 合并组件 | 合并所需的受限凭据 | 不放到 worker，优先保留在 GitHub 侧；hub 不因调度而自动获得合并权 |
| 用户/管理员 | 安装、更新、吊销及修复控制器的权限 | 不交给 worker，不配置通用 sudo 通道 |

即使两个账户 home 分开，也要检查组成员、ACL、父目录、共享临时目录、socket 和进程访问。
不能把控制器 token 放到全局环境，再指望启动 worker 时靠提示词保密。

### 3.3 Agent 能碰到什么、碰不到什么

允许 worker 改自己的源码和构建产物，使用自己的模型登录，读取专门发布的非敏感任务计划。
控制器代码、依赖、策略和证据应由 controller 或 root 管理，worker 无写权；
控制器秘密应对 worker 无读权。需要访问公共计划时，应单独安排可遍历目录，
不能把整个证据目录放开，也不能误把所有父目录设为不可遍历而使任务根本无法启动。

worker 不应拥有 sudo、可提权组、管理服务 socket，或能改启动器及其祖先目录的权限。
控制器收证不读取 worker 可随意替换的文件来认证身份，也不以控制器身份执行 worker 提供的命令。
这些限制成立时，普通 worker 无法直接改裁判；若它获得 root，边界就失效。

两个账户仍共享发行版的内核、系统服务和通常的网络环境。
UID 分离本身不建立出口白名单；Windows 目录若仍被挂载或存在其他宿主通道，
也要单独限制，不能因为采用 A 就省去 ADR 的宿主资料隔离。

### 3.4 实现复杂度及对 ADR 的影响

复杂度为中到高：没有跨 Windows/Linux 的证据传输适配，但要正确维护账户权限、
可信安装、窄启动接口、进程隔离和完整权限链；误配置往往不像语法错误那样明显。
还需单独完成网络控制、可靠收证、超时和多轮恢复。

hub 可继续放在 WSL，但须运行在 controller 身份和独立安装中；Agent 放在 worker 身份。
ADR-0001 的“hub 在 WSL”方向可以保留，但需要补上两个身份和控制器升级边界。
函数式内核仍是纯函数；变化的是哪一个可信外壳加载生效版本并持有凭据。

### 3.5 尚未核实的前提

- 【未核实】本机可用的身份切换机制、有效 UID/组、ACL、进程访问限制及管理员配置，
  能否同时做到“可启动 worker”和“worker 不可反向提权”；不能仅检查账户名字。
- 【未核实】关闭 automount、interop 后，是否仍有手工挂载、转发服务或其他宿主入口。
- 【未核实】各 Agent 的真实工具进程是否处于声明的 UID 和沙箱内；
  尤其 Claude 沙箱在本机 WSL 中是否实际生效，不能照搬 ADR 中“支持 WSL”的描述。
- 【未核实】发行版内网络约束是否覆盖所有 worker 进程及直接连接，模型和 GitHub
  的允许通信能否在同一政策下正常工作；代理环境变量不是强制出口控制。

## 4. 方案 B：控制器在 Windows，Agent 在 WSL

### 4.1 信任边界

候选设计让 Windows 上的可信启动器使用
`wsl -d tandem -u worker -- <agent>` 这一调用形态启动任务。
这只是架构说明，本轮不执行该命令。

```text
+-------------------- Windows host --------------------------+
| trusted controller identity                                |
| protected code + runtime + active policy + hub credentials |
| private evidence (not exposed to worker)                   |
|              |                                             |
|              | wsl.exe: fixed distro / user / executable    |
|              | stdout + stderr + exit / timeout capture     |
| ============= host / WSL access boundary ================= |
|              v                                             |
| WSL: tandem / worker UID                                   |
| Agent + model login + editable repository                  |
| protected in-WSL probe helper, if required                  |
| no host drive access or Windows command bridge for worker  |
+------------------------------------------------------------+
```

“证据存在 Windows”不是权限设置。
必须确认 WSL worker 无法经挂载、interop、共享目录或控制器接口读写这些 Windows 路径。
控制器应使用受保护安装和明确的身份；不能仅把脚本搬到一个前台 Agent 同样可写的目录。
Windows 管理员或可控制 WSL 的宿主主体位于信任边界外层，WSL 内的普通 UID 无法约束它们。

关闭 Linux 向 Windows 的 interop，与 Windows 主动调用 `wsl.exe`，方向不同。
这一点可以解释 B 为何值得验证，但不能据此宣称本机一定可用：
**关闭 interop 后，Windows 发起上述调用、持续接收输出和取得退出状态是否都正常【未核实】。**

### 4.2 凭据由谁持有

| 主体 | 凭据和用途 | 存放及边界 |
|---|---|---|
| Windows controller / hub | 事件采集及确有必要的受限操作凭据 | 控制器身份可读的存储；不放进 worker 命令行、任务文本或环境 |
| WSL worker | 模型登录材料 | 仅存在 worker 可用的 Linux 环境；不复制整个个人发行版的凭据 |
| 可选的 Git 成果提交接口 | 仅候选分支写入等最小权限 | 可信侧单独持有并约束操作，不能等价成合并接口 |
| GitHub 合并组件 | 最终合并权限 | 留在 GitHub 侧的受保护组件；不进入 WSL，也不由本地证据直接驱动绕过检查 |
| 用户/管理员 | Windows 控制器安装与 WSL 维护权限 | 不提供给后台 Agent |

Windows 凭据存储本身的安全性、账户 ACL 和服务运行方式【未核实】。
若控制器只是日常登录账户中的进程，同身份前台工具仍可能访问其资料；
若要防这些工具，需要进一步分账户，并验证跨账户启动 WSL 的可行性。

### 4.3 Agent 能碰到什么、碰不到什么

worker 可以修改 Linux 工作区、产生输出和使用自己的模型凭据。
若宿主通道确实被关闭，它不应能读 Windows 私人资料、改控制器代码或覆写已封存证据。
它仍可以在输出里撒谎、隐藏工具调用、尝试联网或留下后代进程；B 没有消除这些能力。

控制器直接捕获输出可解决“worker 事后替换证据文件”，但不能单独解决第二轮 N2。
例如 Agent 打印假拒绝仍只是普通字节。要验证文件访问，可能需要 WSL 内一段
由管理员安装、worker 不可写的固定探测辅助程序，或来自权限执行层的可信记录；
该辅助程序也属于可信代码，不能从 worker clone 导入。
探测必须说明实际覆盖账户权限还是完整 Agent 工具沙箱，不能混为一谈。

Windows 文件上的诱饵可用于测宿主访问边界，Linux 受保护副本可用于测 UID/工具边界，
两者代表不同能力；一个被挡住不能替代另一个。
禁止访问的测试目标应是合成资料，不试读真实私人密钥。

### 4.4 实现复杂度及对 ADR 的影响

边界位置比较直观，初步的进程捕获实验可以很小；完整实现复杂度仍为中到高，
不能把“小实验容易”理解成“系统已经安全”。跨系统的参数、编码、路径、取消、
退出码、输出量限制及清理后代进程都需要适配。
Windows 控制器仍会处理恶意输入，需要防路径逃逸、链接/重解析点、坏事件和日志泄漏。

本方案把 hub 的可信部分放在 Windows：事件采集、固定裁决、日志和凭据均在可信侧；
WSL 留给 Agent 和必要的受保护执行辅助程序。不能只搬裁判却把持 token 的 hub
继续放在 worker 的身份下，那会留下本题的另一半风险。

这会改变 ADR-0001 关于 hub 放在 WSL 的决定，以及 PRD 的 M1 表述，
应在用户选择后另行更新；本文件不修改这些文档。
内核仍保持纯函数，GitHub 仍掌握最终合并权。
ADR 对 Windows 原生 Agent 的顾虑也仍有效：B 把 Agent 留在 WSL，
并不要求在 Windows 控制器账户下运行能任意改文件的 AI。

### 4.5 尚未核实的前提

- 【未核实】本机 Windows 10/WSL 版本在关闭 interop 和 automount 后，
  宿主能否以指定发行版和 worker 身份启动进程并可靠收取两路输出及退出码。
- 【未核实】选定的 Windows 控制器账户能否访问并启动目标发行版；
  不能假定当前用户可见的 WSL 注册在另一个账户下也直接可见。
- 【未核实】worker 是否确实不能通过其他挂载、共享、网络服务或命令桥接接触宿主；
  只看一份 `wsl.conf` 的哈希不足以确认生效状态。
- 【未核实】Claude 等 Agent 的沙箱是否在该启动方式下生效，
  登录材料、工具事件格式、取消及超时是否与交互运行一致。
- 【未核实】取消宿主进程是否清理 WSL 后代，以及睡眠、重启后如何识别残留任务；
  结束 `wsl.exe` 不能直接当作已证明所有后代退出。
- 【未核实】网络出口约束和允许通信仍需另行验收；换控制器位置不改变网络证据缺口。

## 5. 方案 C：先暂停后台准入

### 5.1 信任边界与凭据

```text
+---------------- trusted user -------------------+
| manual review / foreground work / GitHub checks |
| no unattended controller granting admission     |
+-----------------------+-------------------------+
                        | explicit foreground task
======================== human review boundary ===
                        v
                Agent + editable repository
                output remains untrusted
```

C 暂停的是未经验证的后台执行，不必暂停全部开发。
可以继续前台 herdr 派活、离线内核测试和文档审查，但仍按前台工具实际权限使用它们。
这张图里的人工审查是工作流程约束，不是操作系统沙箱，不能使前台 Agent 天然隔离。

不启动持有后台 token 的常驻 hub，不向 Agent 增发合并凭据。
前台 Agent 保有其运行所需的模型登录材料及已有的、用户明确授权的能力；
私人资料访问风险取决于前台环境，不能宣称 C 能保护同账户资料。
GitHub 合并权限仍由现有受保护流程/用户掌握，不能用“暂时手动”绕过 CI。

### 5.2 复杂度、ADR 影响和未核实前提

近期新增实现复杂度低，没有新的可信控制器，也没有新的后台隔离保证。
代价是 M1 的无人值守部分顺延，人工派活和审查负担持续存在。

这与 ADR 的“诱饵测试未通过就只在前台使用，后台顺延”相容；
hub 的最终位置暂不重选。即使本地模拟循环可运行，也不能称后台 M1 已验收。

【未核实】用户能接受多久的人工负担，以及暂停期间是否仍有旧后台进程或宽权限凭据
需要盘点；本轮未查询或停止任何进程，也未吊销凭据。
若选择 C，可约定以 A/B 的最小实验结果作为重启决策的依据，避免无限期等待。

## 6. 对比：按前提成立时的能力比较

这里的安全性是条件分析，不是本机测量分数；A/B 的关键前提失败时均不得后台准入。

| 维度 | A：同发行版分用户 | B：Windows 控制器 + WSL worker | C：暂停后台 |
|---|---|---|---|
| 防 worker 改裁判/读控制器凭据 | 依赖完整 UID、目录、进程和启动器权限链 | 依赖宿主访问边界、Windows 控制器身份和可信安装 | 不新增后台控制器风险；不保护现有前台同账户资料 |
| 防伪造“被挡住” | 仍需独立操作证据，不能只信 stdout | 仍需独立操作证据；宿主捕获只保证收录来源 | 不作后台准入认证，输出继续由人审阅 |
| 网络和沙箱保证 | 必须单独验证 | 必须单独验证 | 不宣称已验证，不因此开放后台 |
| 实现/维护复杂度 | 中到高；Linux 权限和窄启动机制是重点 | 中到高；跨系统进程管理及宿主通道是重点 | 新增实现低，持续人工负担较高 |
| 对 M1 进度影响 | 位置变化小，需重做可信安装和权限验收 | 改 hub 部署位置，先增加一个边界实验 | 后台明确延期，内核和前台流程可继续 |
| 可测试性 | 可做真实双 UID 权限矩阵；同用户 mock 不足 | 可先测宿主启动/收证，再测反向访问；需两侧证据 | 可验证手动流程，但不产出后台隔离通过证据 |
| 主要失效条件 | worker 可提权、可改导入依赖或能读控制器进程 | 宿主通道未关、宿主同身份工具能改裁判、跨账户假设不成立 | 暂停名义下仍留下无人值守进程或把人工审查当沙箱 |
| ADR 改动范围 | 补身份、可信安装与升级流程 | 调整 hub 所在位置，并同步 PRD M1 | 保留原定方向，记录后台顺延 |

本轮不增加第四种架构。独立虚拟机或远程控制器可以成为后续选项，
但会增加部署、通信和凭据管理成本；它们同样不能把 Agent 自述自动变成可信事实。

## 7. 若用户选 B：最小可行的第一步

第一步只做一个“Windows 能启动低权限 WSL 进程并保护收证”的小实验，
不搬完整 hub、不连接模型、不接入 GitHub token、不授予后台准入。
以下是下一任务的范围建议，本轮没有实施：

1. **先约定实验身份和隔离范围。** 固定候选发行版、worker、Windows 控制器身份，
   只用合成资料；列出代码、运行时、策略、输出和诱饵的所有者及读写矩阵。
   若需新建账户、调整 WSL/ACL，先列出具体变更供用户批准，不在实验入口里偷偷修改。
2. **先验证调用方向。** 在用户批准配置的实验环境里，从 Windows 启动固定的本地
   非 AI 测试程序，确认指定 UID、关闭 interop 后的启动行为、两路输出和退出码。
   若该账户无法启动发行版，先停在这个前提，不用恢复宽宿主权限来凑通流程。
3. **验证收证目录及安装的反向保护。** Windows 控制器生成唯一轮次和固定范围内的输出路径，
   直接捕获流；从 worker 尝试修改合成控制器文件、读取合成秘密和覆写证据。
   成功越界或无法确定时记为失败/未验证；不得仅用 worker 打印的拒绝文字认定阻断。
4. **加最小反例和故障验收。** 使用本地测试程序打印假拒绝、假 JSON 和路径逃逸字段，
   测试坏事件、超量输出、超时及后代进程；证明这些输入不能生成“隔离通过”结论、
   不能改变输出位置，缺少证据时能明确停止。先封存现场再清理，仅处理本轮创建的副本。
5. **产出有边界的实验记录。** 保存控制器版本、实际身份的核验来源、WSL/工具版本、
   配置与生效检查、原始受保护证据和脱敏报告，说明本轮只验证了什么。
   UID/版本不能只取自可伪造 JSON；未知项仍标未核实。即使实验成功，
   下一步仍需验证真实 Agent 沙箱、网络出口与允许通信，当前网络不准入限制保持不变。

## 8. Codex 的意见，仅供参考

我的倾向是：若用户愿意先做一个范围很小的边界实验，优先验证 B，
同时在实验及后续验收完成前保持 C 的后台暂停状态。这是推进顺序的建议，
不是代用户选择架构，也不是宣布 B 已经成立。

理由是，B 把日常容易混淆的两份东西分开了：WSL 中允许 Agent 修改的仓库，
与宿主上实际运行的裁判及证据。这个边界容易解释，也能先用非 AI 程序验证。
代价则很明确：hub 部署方向要变，跨系统进程管理要新增，
Windows 控制器身份和宿主访问通道仍需严肃核实；直接捕获 stdout 也没有解决伪证语义。

若用户更重视保留“hub 在 WSL”的方向，并愿意维护完整的双 UID 权限链，
A 仍是成立的候选，不能因它与 worker 同处一个发行版就断言一定不安全。
若目前不愿承担任一方案的验证成本，C 与现有 ADR 的退路一致，
可以继续前台开发而明确延后后台目标。

用户最终需要权衡的是：愿意先验证哪一条边界、愿意维护哪一侧的复杂度，
以及能接受多长时间的后台延期。待用户写下自己的倾向并拍板后，
再另行形成 ADR 决定和实施任务。
