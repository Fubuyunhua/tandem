## 背景
本 ADR 回答两个问题：
1. **系统由哪些模块组成，判断由谁来做**（参见 PRD 3.5「分工」、第 4 节）
2. **常驻后台服务在哪里运行**（参见 needs-spec R8）

约束条件：
- 运行在 Windows 10 上，交互界面用 herdr。
- 使用订阅额度：Claude Pro、ChatGPT Plus、OpenCode Go。
- 核心模型（MOD-1 至 MOD-4）要方便你推导和测试。
- 后台 AI 无人值守，因此需要隔离。

## 问题 1：模块与判断

### 备选方案
- **A. 纯规则**：所有判断都写成固定代码。
  - 好处：可预测、可测试。
  - 代价：任务类型、语义风险这类需要理解内容的判断，规则难以穷尽，维护成本高。（评审第 11 条后修正：原来写的是"写不出规则"，说得太绝对。）
- **B. 全部交给模型**：判断全靠模型加提示词。
  - 好处：灵活。
  - 代价：会出错，会被 Issue 里的文字带偏（提示注入）。autoloop 的 askFirst 只写在提示词里，已经证明这种约束没有强制力。
- **C. 规则底线 + 模型意见 + 代码裁决**（讨论中形成）：
  - 底线由固定规则守住；
  - 语义判断由"分诊顾问"（模型 + 提示词）给出意见；
  - 最终由决策中心的固定代码裁决。

### 讨论记录（你在审第一版图纸时提出的问题）
1. 执行器和 Agent 之间的箭头没标明传的是什么。→ 已修正：执行器向 Agent 传"任务说明"，Agent 向执行器回"回执"。
2. **判断不能全靠硬编码，模型应该参与，用"固定代码 + 提示词"。** → 由此形成方案 C。
3. 缺少回滚设计。→ 作为横切规则补上，见下文。
4. 缺少学习模块。→ 已补上，并采用你提出的六步闭环。
5. AI 补充的两处遗漏：定时器、额度统计。

### 裁决原则（已达成一致；按评审第 3 条修订）
- **每次都根据真实改动重新算级别**：先由规则从改动里算出"基础级别"，模型意见只能在基础级别上调整一次，不能在上一次的结果上接着调。这样就堵住了连续降级。
- **底线区，模型只能调严**。底线区用机器能判断的条目来定义（见下方"底线条目"），不用"安全/权限"这类类别名称。
- **可放宽区，模型可以调松**（你提出的例外）：
  - v1 只包括**纯文档**。测试、样式、外围代码暂时都不放宽，等有了真实数据再逐步开放。
  - **哪些属于可放宽区由规则划定，不由模型判断**，以免模型自己给自己松绑。
  - 最多下调一级，最低降到 B。
  - 被放宽的事项提高抽查比例。抽查发现放宽错误时，这一类收回放宽权限。
- 提示词也是决策逻辑的一部分：纳入版本管理，归你所有，修改提示词按 D 级处理。
- **完成与否只看外部证据**（评审第 7 条）：Agent 的回执只是自述；以 GitHub 上那次提交的 CI 结果为准。**CI 不通过，任何人都不合并**，回滚也一样。修 bug 的 PR 必须附带回归测试（修改前失败、修改后通过）。

### 底线条目（AI 草稿，待你改）
只要改动命中下面任意一条，基础级别就是 D。目录名是占位，ADR-002 定下目录结构后再改。

| 类型 | 条目 | 怎么判断 |
|---|---|---|
| 路径 | 决策中心 `core/**` | 改动的文件路径 |
| 路径 | 闸门本身：`.github/**`、`risk.yml`、闸门调用的脚本 `scripts/gate/**` | 同上 |
| 路径 | 提示词 `prompts/**` | 同上 |
| 路径 | 依赖清单：`package.json`、各类 lock 文件、`pyproject.toml`、`requirements*.txt` | 同上 |
| 路径 | 数据迁移 `**/migrations/**` | 同上 |
| 路径 | 密钥相关：`.env*`、`*.pem`、`*.key` | 同上 |
| 动作 | 删除文件 | diff 里有删除 |
| 动作 | 改名或移动 | **改名前、改名后两个路径都参与判断，取更高的级别**（堵住"挪进 `docs/`"） |
| 动作 | 测试文件里的断言数量减少 | 数 `assert` / `expect(` 的个数。这是近似判断，可能误报，但宁可多报 |
| 动作 | 命中密钥扫描 | 用 gitleaks 一类工具扫 diff，**文档也扫** |
| 动作 | 发布或对外发送：打 git tag、发 release、发包、给外部发消息 | **在工具层硬拦截**（终审第 4 条）：Agent 拿不到发布权限，网络只放行白名单地址；拦截代码放在受保护的 `scripts/gate/**` 里，不靠执行器去"识别" |

**拆 PR 的处理**：同一个 Issue 产生的多个 PR，按合计改动算级别。

### 基础级别怎么算（AI 草稿，待你改）
（终审第 4 条修订：**先查底线，再看是不是 A**。原来的顺序会把"给外部发消息"这类不改仓库的动作判成 A。）
1. 命中任何一条底线条目（不管改没改仓库）→ **D**
2. 不改仓库、也没命中底线的动作（给 Issue 加 label、在仓库内写评论、生成报告）→ **A**
3. 其他所有改动 → **C**
4. 模型意见：可以把任何级别往上调；只有当**所有改动的文件都是纯文档**时，才可以从 C 下调到 **B**

也就是说，v1 里 B 级只会来自"纯文档 + 模型同意放宽"这一种情况。

### 等级 → 流程表（AI 草稿，含你的决定）
| 等级 | 典型情况 | 开工 | 审查 | 合并 | 你要看什么 | 抽查（初始值） | 通知 |
|---|---|---|---|---|---|---|---|
| **A** | 加 label、写评论、生成报告 | 自动 | 不需要 | 不涉及 | 不用看 | 每周抽 10% 看日志 | 周报 |
| **B** | 纯文档 | 自动 | 另一家模型审一次 | CI 绿 + 审查通过后自动合并，**绑定提交编号** | 不用看 | 合并后抽 30% | 日报 |
| **C** | 普通代码、bug 修复 | 自动 | **至少 2 家审核者都要通过**（你的决定），来自不同提供方，都不能是写手 | CI 绿 + 审核全部通过后自动合并，**绑定提交编号**（你的决定：C 级不需要你批准） | 不逐个批准；你仍然可以查看 | 理解抽查：**每天固定抽 1 个**，两周后再调（你的决定） | 日报 |
| **D** | 命中底线条目 | **你先批准方案再开工** | 至少 2 家审核 + 你在桌面看完整 diff（终审第 13 条你回复"同意"） | 你批准，**永不自动合并** | 完整 diff 和改动理由 | 不需要 | 立即推送（安静时段也推） |

几条附加规则：
- "另一家"按**模型提供方**算，不按工具算。OpenCode 跑 GPT 系列模型时，和 Codex 算同一家；跑 Claude 时，和 Claude Code 算同一家。
- 写过代码的 AI 提供方都记在任务历史里，换手时也不清掉，它们都不能担任这个任务的审核者。
- **多家审核的规则**（终审第 2 条，你的决定）：任何一家不通过，代码就退回修改；改完以后，之前的审核结论全部作废，所有审核者重新审。**不设仲裁**：写手拒绝修改时，直接进入"待你介入"。
- **运行模式**（终审第 1 条）：
  - 单 Agent 模式（M1，只有 Claude）：没有人能审查，所以**所有等级**都由你批准，记录里标明"这次没有 AI 审核"。D 级照样要先批准方案。
  - 多 Agent 模式：按上表执行。凑不齐合格审核者时，任务进入"待你介入"。
- **额度未知时**（终审第 15 条，你的决定）：默认还有额度；遇到"额度用完"的报错，就把这一家标记为用完，并在记录里注明"额度是估计值"。M3 做调度器时再改。
- **等级可以修改**（你的决定）：等级的划分和这张流程表都写在配置文件 `risk.yml` 里，不写死在代码中。这样以后可以把 C 级再拆细，比如拆成 C1 和 C2，而不用改内核代码。修改 `risk.yml` 本身按 D 级处理。
- **`core/` 的审核规则**（你的决定，在状态流转走查后修订）：AI 和你都可以改 `core/`。
  - AI 改的：必须经过你批准。
  - 你改的：必须经过 AI 审核，但**你有权直接批准自己的代码**，所以 AI 审核起的是提醒作用，不能否决你。CI 照样不能越过。
  - 否决 AI 的审核意见时，要对每一条反对意见写一句理由，并绑定当前的提交编号和审核标准版本；有新提交进来就要重新确认。否决必须由你在界面上明确操作，不能因为"提交作者是你"就自动放行。
  - 以后复盘时统计"否决的地方，事后证明是你对还是 AI 对"，作为批判能力的指标。结论分三种：已确认、待验证、无法判断。
  - 参与过的 AI 都要注明。
  - 无论哪种情况，你都必须参与。
- 不可逆的动作，执行前必须先备份。
- 抽查比例是占位数字，以后由 MOD-4（抽查采样）算出来。

### 任务状态流转（评审第 5 条）
每个任务都有状态，按 `docs/design/task-lifecycle.md` **第七版**流转（你设计的，13 个状态，已按终审修订）。要点：
- 回执必须带任务编号、第几次尝试、提交编号。每次收到回执，都**按真实改动重新算级别**；升成 D 级而方案还没批准时，任务转去"待你批准方案"。
- 批准绑定方案版本，审核结论绑定提交编号。有新提交进来，旧的审核结论、批准和否决全部作废。
- 从异常恢复时，先去 GitHub 核对还没确认的动作实际结果如何，再决定回到哪个状态；已经开始合并的任务不能取消。
- 回执、CI 状态变化这类事件**只走规则，不调用模型**，防止"回执 → 分诊 → 新任务 → 回执"这样的循环消耗额度。
- "你的回答"只有一个入口：通知模块收到后，作为新事件交给事件采集。
- 执行器设超时，可以强制结束 Agent 进程；定时存活检查，并在程序启动和电脑唤醒时先检查一遍。

### 第三版架构（按评审第 10 条修正：分清"数据往哪流"和"谁调用谁"）
```
 定时器 ─┐
 GitHub ─┼─► [事件采集] ──事件──► [分诊顾问] ──事件 + 意见──┐
 回执 ───┤                       模型 + 提示词              │   （回执、CI 事件跳过分诊，只走规则）
 你的回答┘                       （只出意见）                │
                                                           ▼
 [记录：日志 · 任务记录 · 额度 · 信任 · 理解债]      外壳：读出快照
            │                                        （任务记录、策略、额度、信任、当前时间）
            └──────────────── 读 ──────────────────────────┤
                                                           ▼ 作为参数传入
                                                [决策中心] 内核纯函数
                                         decide(...) → 新状态 + 动作清单
                                                           │ 返回值
                                                           ▼
                                            外壳：先保存，再执行动作
                      ┌────────────────────┬───────────────┴──────────┐
                      ▼                    ▼                          ▼
                  [执行器]               [通知]                      [学习]
           任务说明 ▼  ▲ 回执         卡片 ▼  ▲ 回答           练习/材料 ▼  ▲ 你的答案
       Claude / Codex / OpenCode      你的手机                   你（桌面）
       回执和回答都回到事件采集，作为新事件
```
- 内核**不调用**任何东西：它不读存储、不读时钟、不调 GitHub、不自己取随机数。所有输入都由外壳读好后作为参数传进来，输出是"新状态 + 动作清单"。
- 外壳把数据传给内核，这是合法的；违规的是内核自己去读外部。（这是第 10 条讨论中 Codex 纠正的地方。）
- 内核签名的候选：`decide(任务记录, 事件, 策略, 额度快照, 信任快照, 当前时间) → (新状态, 动作清单)`。最终签名由你在 M1 写内核时定。

| 模块 | 职责 | 内核/外壳 | 谁写 |
|---|---|---|---|
| 事件采集 | 把 GitHub 动态、定时器、你的回答、回执统一成"事件" | 外壳 | AI |
| 分诊顾问 | 用模型给出语义意见，只出意见 | 外壳（调用模型属于外部交互） | 提示词由你写，接入代码由 AI 写 |
| **决策中心** | 守底线、按状态流转裁决、运行你写的模型 | **内核** | 你主写；AI 也可以改，按 `core/` 审核规则 |
| 执行器 | 把动作翻译成任务说明，启动 Agent，收回回执；超时就结束进程 | 外壳 | AI |
| 通知 | 发卡片、收回答 | 外壳 | AI |
| 学习 | 走六步闭环（见下） | 判断在内核，交互在外壳 | 规则由你定，实现由 AI 写 |
| 记录 | 日志、任务记录、额度、信任统计、理解债，只追加 | 外壳 | AI |
| 定时器 | 按时间产生事件，包括存活检查 | 外壳 | AI |
| ~~调度器~~ | 派给谁、什么时候跑。**暂缓**（评审第 4 条，你的决定），M1 只记录每个任务实际消耗了多少额度 | 内核 | 你（M3） |

模块之间的数据格式（"合同"，由你定义）：**事件**、**决定**（新状态 + 动作清单）、**回执**、**任务记录**、**评审记录**（评审第 9 条新增）。

### 横切规则（每个模块都必须遵守）
- **可回滚**（按评审第 6 条修订）：
  - AI 对代码的改动：每次改动是一个 PR，合并时压成一个提交，用 `git revert` 撤回。
  - main 分支 CI 变红时，系统**不自动合并回滚**，只做三件事：生成回滚方案、暂停相关任务、通知你。由你一键批准。回滚的目标是"**最后一次 CI 通过的版本**"。回滚 PR 同样要通过 CI；如果是 CI 本身坏了，就先修 CI。
  - 系统自身的规则、提示词、模型：用 git 做版本管理，日志里记录每个决定用的是哪个版本；新规则先以影子模式运行，确认无误再生效。
  - 不可撤回的动作一律定为 D 级，执行前先备份（删数据前先导出，发消息前先记录）。
  - 降级写成一条新记录，不修改旧记录。
- **箭头只传数据**：模块之间只通过上面列出的数据格式通信。
- **只追加**：记录只新增，不修改、不删除。
- **可重放**（评审第 8 条）：
  - 当前状态由日志重放得到。重放只还原事实，不重新执行动作：每个动作都有编号和执行回执，重启后只核对没有确认完成的动作（比如先去 GitHub 查 PR 的真实状态）。
  - 每次做决定时，保存输入快照（先脱敏，保存模型实际收到的那一份）和模型的原话；重放时用保存的意见，不重新调用模型。
  - 每次抽查都记录这一项实际被抽中的概率，并标明样本类型：随机抽中、有分歧必查、事后暴露。信任统计按任务类别和模型版本分组。

### 学习模块的六步闭环
| 步骤 | 谁做 |
|---|---|
| 1. 遇到问题 | 系统自动捕捉：标了"说不清"的地方、评审意见不一致、预测出错 |
| 2. 抽象出共性 | AI 提出，**你确认** |
| 3. 相关的已有知识 | AI 查找 |
| 4. 练习 | AI 出题，你来做 |
| 5. 总结 | **只能你写** |
| 6. 形成记录 | 系统保存；下次遇到同类问题时，按标签匹配，主动提醒你 |

补充规则（评审第 9 条，你的决定）：
- **先保存你的答案，再展示 AI 的意见。** 手机通知的标题和摘要也不能提前透露结论。如果你已经在别处看过 AI 的意见，这次记录就标为"非独立"，不计入独立发现率。
- 学习产出写成记录就算完成。**只有真正要修改规则或提示词时，才按 D 级流程走。**
- 同时进行中的学习任务**最多 3 个**。超出的排队等待，不会被丢弃。
- 发现率 = 你独立发现的有效问题 ÷ 双方发现的有效问题（去重后）。双方都没发现问题时，记为"不适用"。

样本见 `learn/records/0001-判断与执行分离.md`。

## 问题 2：后台常驻服务在哪里运行

### 方案 A：WSL2（专用发行版，关闭 automount 和 interop）
- 好处：
  - 隔离：配置得当时，AI 碰不到你的浏览器登录状态、密钥和个人文档【待诱饵测试验证】。
  - Claude Code 的沙箱支持 WSL2，不支持 Windows 原生（已查官方文档，见评审第 1 条）。
  - 参考实现大多基于 Linux。
- 代价：
  - 需要重新安装和登录各家 AI。
  - 需要保活【未核实：WSL 空闲时是否会自动关停】。
  - 多一层虚拟机：占用内存，排查问题更麻烦。
- **注意**：WSL 默认不隔离，它会自动挂载 C 盘，也能调用 Windows 程序。必须专门配置才算隔离。

### 方案 B：Windows 原生
- 好处：环境现成，和 herdr 在同一处，自启动简单。
- 代价：
  - 无人值守的 AI 以你的身份运行，能访问你的整个用户目录。

## 决定
**问题 1：采用方案 C。** 先由规则从真实改动里算出基础级别，模型只给意见，最后由内核纯函数裁决。等级和流程写在 `risk.yml` 里，任务按状态流转推进。合并权只在 GitHub 闸门手里：CI 不通过，任何人都不合并。

**问题 2：后台常驻服务运行在 WSL2 的专用发行版里。** 每家 Agent 通过诱饵测试后，才允许无人值守运行。

已决定 ≠ 已验证。以下几项是**验收项**，还没有在本机验证：
- **诱饵测试**（终审第 10 条修订）：每家 Agent 分别尝试做三件事，都要被挡住：
  - 读取私人密钥和诱饵文件；
  - 修改**正在生效**的配置（仓库里的 `risk.yml` 可以改，但要走 D 级）；
  - 访问白名单以外的地址。
  
  同时要验证允许的通信能正常进行，比如调用模型、访问 GitHub。
  - **没通过怎么办**：哪一家没通过，这一家就只在前台 herdr 里用，不进后台。
- WSL 关闭 automount 和 interop 之后，各家 Agent 能否正常工作；
- 电脑睡眠或重启后，能否恢复到正确的状态；
- 分支保护：私有仓库是否需要升级 GitHub Pro；勾上"管理员也不能绕过规则"；
- **凭据清单**：M1 开工前单独写一份，列出后台服务、Agent、合并组件各自持有哪些凭据、有什么写权限。Agent 不能拿合并权限，也不能改检查结果。

## 代价
- **C 级不逐个批准。** 你仍然可以查看，但理解债主要靠每天 1 个的抽查来发现，抽不到的改动可能一直没人看。
- **C 级要至少 2 家审核都通过，而且不设仲裁。** 换手以后**可能**凑不齐审核者，任务会进入"待你介入"，实际频率要记录下来。这会拉低自动完成率，PRD 里"一半以上任务自动完成"的目标可能受到影响。
- **M1 是单 Agent 模式**：所有任务都要你批准，M1 阶段不会有任何自动合并。
- **你可以否决 AI 对你代码的审核意见。** 这样 `core/` 的保护就从"双方同意"变成了"你必须参与 + CI + 留下记录"。

- **调度器暂缓。** M1 到 M3 之间，后台用 Claude 时没有额度保护。
- **WSL2**：要重新安装和登录各家 AI，占用内存，排查问题多一层。
- **改 `risk.yml` 和提示词都是 D 级**：调整规则的速度会变慢。
