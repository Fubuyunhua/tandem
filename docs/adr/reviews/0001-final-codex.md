# ADR-0001 定稿前终审 · codex

依据：ADR 定稿候选、任务状态流转第六版及后续补充、评审汇总、PRD v1.1。未读取其他评审者本轮的 `0001-final-` 输出。

以下指出文档合同的问题，不表示已经复现实现漏洞；WSL2、C 级自动合并且多家审核通过、用户保留最终决定权、CI 不可越过、调度器暂缓等已有决定不重新表决。本机隔离、实际额度与各适配器能力【未核实】。

## 1. M1 的人工兜底没有进入状态表，照表执行会无法派活或停在待 AI 审核

- **问题**：PRD/ADR 允许 M1 由用户代替缺席的审核者，但状态表仍把独立 AI 审核作为必经条件，且 D 级没有明确的单 Agent 例外。
- **证据**：
  - `docs/PRD.md`「M1」：“只接一个 Agent（Claude），所以 B、C 级也由你批准”。
  - `docs/adr/0001-overall-architecture.md`「附加规则」：“只有一家可用时（例如 M1 只有 Claude），没有人能审查，B、C 级都改为由你批准。凑不齐多家审核者时，任务进入‘待你介入’。”
  - `docs/design/task-lifecycle.md` 第六版第 1 条：派活条件是“写代码的 Agent 和至少一家审核者有额度”；第 9 条：CI 绿后到“待AI审核”；第 12–15 条只有收到审核结果后的转换，没有“没有合格审核者”的转换。
  - ADR 的 D 级审查列是“多家审核 + 你在桌面看完整 diff”；PRD M2 才安排“飞书卡片和摘要”。
- **建议**：补一条覆盖全状态表的 M1 能力规则：无人可审时如何派活、CI 绿后进入哪个人工状态、用户在哪里提交批准及理由；M1 可用本地界面或 CLI，但入口需要明确，不能依赖 M2 飞书。尤其是系统开发必然会遇到 `core/`、依赖或闸门变更：M1 的 D 级是等待外部人工调用另一家审核，还是另设用户批准的阶段例外，需用户决定，不能悄悄扩大 B/C 的例外。记录额度是可实施的目标，但订阅剩余额度及单任务消耗的读取方式【未核实】；M1 还应允许“未知/人工录入”，或者明确将自动读取作为开工前的 spike 验收项，不把未知当成有额度。无需因此恢复已暂缓的调度器。
- **严重程度**：高

## 2. 多家全通过的决定与单个审核、仲裁直接放行的转换相冲突

- **问题**：状态表仍按单个“审核通过”推进，仲裁甚至能在原审核者反对时直接送入待合并，无法执行最新的 C 级全体通过要求。
- **证据**：
  - `docs/adr/reviews/0001-summary.md`「新 3」用户回应：“C 级要多家审核都通过。”
  - `docs/PRD.md` F6：“C 级要多家审核都通过。”
  - `docs/design/task-lifecycle.md` 第六版第 12 条：“待AI审核 → 待合并”，条件仅“不是 D 级”；第 16 条：“待仲裁 → 待合并（D 级则到‘待你审核’）”，触发是“仲裁者认为写手对”。
  - 同表第 20 条仅检查“提交编号和审核时一致”，未要求指定的审核集合全部完成。
- **建议**：用户确定“多家”的最小数量、是否必须来自彼此不同的提供方，以及这一轮的必需审核者集合；每项结果绑定 SHA/标准版本，只有集合齐全且通过才推进。仲裁是澄清或撤销某项反对意见，还是能替代一个必需审核者，须用户明定；在此之前不能把仲裁同意等价为全体通过。人工最终否决权可保留为独立、有理由的覆盖操作，不与“AI 全部通过”混记。同样补上“合格审核者不足→待你介入”，与 ADR 对齐。
- **严重程度**：高

## 3. A 级优先规则可以直接吞掉对外发送、发布等 D 级底线

- **问题**：基础级别算法先按是否修改仓库返回 A，和“任一底线命中就是 D”矛盾。
- **证据**：
  - `docs/adr/0001-overall-architecture.md`「底线条目」：“只要改动命中下面任意一条，基础级别就是 D”；动作包括“发布或对外发送：打 tag、发 release、发包、给外部发消息”。
  - 同文件「基础级别怎么算」第 1 条：“不改仓库的动作（打标签、写评论、生成报告）→ A”；第 2 条却限定为“改了仓库，命中任何一条底线条目 → D”。
  - `docs/PRD.md` F2：“取所有匹配项中的最高级。”
- **建议**：先匹配所有动作与路径底线，再决定未命中者是否属于 A；不能提前按“不改文件”短路。另需用户划清“普通内部评论/系统通知”和“对外发送”的边界：否则评论可能走 A 绕过审批，也可能全部落 D，使每张例行通知都要先批准。工作通知可否预先授权、授权到哪些收件人和内容范围，应成为显式策略；风险等级、是否产生 PR、需要哪些批准分别表达，不强迫非代码动作走“待合并”。这修正算法一致性，不是替用户降低发送动作的等级。
- **严重程度**：高

## 4. 状态记录未绑定方案、标准与审核版本，也缺少实际 diff 升级为 D 的入口

- **问题**：ADR 的版本绑定原则没有落实到任务合同，处理中的实际改动升级和旧批准失效均无可执行转换。
- **证据**：
  - `docs/adr/0001-overall-architecture.md`：「每次都根据真实改动重新算级别」；D 级要求“你先批准方案再开工”；人工否决要“绑定当前的提交编号和审核标准版本；有新提交进来就要重新确认”。
  - `docs/adr/reviews/0001-summary.md` 第 10 条讨论结论：“‘批准’要绑定具体的方案版本或提交编号。有新提交进来，旧的批准就失效。”
  - `docs/design/task-lifecycle.md` 第六版第 3 条只写“标记‘方案已批准’”；第 5 条只要求“不是 D 级，或者方案已批准”；任务信息只列“方案是否已批准”和“最新的提交编号”。
  - 同表第 23 条：改审核标准直接到“待AI审核”，只要求“新的标准版本，审核计数清零”。
- **建议**：任务记录增加方案版本/范围、批准对象、当前政策版本、每份审核证据及其 SHA/标准版本；明确新提交使哪些审核和人工否决失效，标准变更使哪些结论重审，不能只清零计数。方案批准可绑定方案范围，不必错误地让每次符合方案的提交都重批方案。具体走查：C 级“改样式”实际改了依赖，验收前应重算为 D，并在继续实施前取得方案批准；不应沿用旧等级走 C 自动合并。政策更改本身按 D 审批后，才能启用新标准；修改计数不能借换任务或版本反复清零而不留下历史。
- **严重程度**：高

## 5. 无人值守的隔离验收仍缺少允许能力与受保护对象的区分

- **问题**：“外网访问全部挡住、risk.yml 不可改”的字面验收，与模型/GitHub 通信及 AI 提交规则变更的流程没有对齐，可信凭据持有者也未明确。
- **证据**：
  - `docs/adr/0001-overall-architecture.md`「决定」：“每家 Agent 通过诱饵测试后，才允许无人值守运行”；验收项为“读诱饵文件、改 risk.yml、访问外网，三项都要被挡住”。
  - 同文件允许 AI 改 `core/`，并将“修改 risk.yml 本身按 D 级处理”；执行器负责“启动 Agent，收回回执”。
  - 同文件「决定」：“合并权只在 GitHub 闸门手里”；`docs/PRD.md` F3：“机器人账号，只开最小权限，不授予 Workflows 权限。”
- **建议**：将验收写成“禁止读取私人/控制器秘密、禁止改运行中策略、禁止未授权出口”，同时验证允许的模型通信、GitHub 交互能成功。若联网由可信代理代办，也应写明路径。区分任务 worktree 里可供 D 级评审的 `risk.yml` 修改，与只允许受信部署流程更新的生效副本。列出 hub、worker、GitHub 检查/合并组件各自的凭据与写权限；worker 不拿合并和改检查结果的权限。“GitHub 闸门”是约束，不足以指明哪个主体真正执行合并。WSL2 选择不变；这些是 M1 前要验收的边界，本机是否满足【未核实】。
- **严重程度**：高

## 6. 异常与取消转换仍可能重做动作或宣告取消一个已经合并的任务

- **问题**：通用“回到旧状态重试/任何非终点可取消”与后补的动作核对、合并中不可取消规则没有统一。
- **证据**：
  - `docs/design/task-lifecycle.md` 第六版第 27 条：“异常 → 出问题前的状态”，条件是“—”；第 28 条：“任何非终点状态 → 已取消”。
  - 同文件取消补充：“待合并，且合并已经开始……不能取消”；异常转换第 8 条只覆盖“处理中”，存活检查也只检查“处理中”。
  - `docs/adr/0001-overall-architecture.md`「可重放」：“每个动作都有编号和执行回执，重启后只核对没有确认完成的动作”。
- **建议**：将补充规则提升为表中的守卫条件：执行合并动作与接受取消应在同一任务版本上互斥；请求已发出但响应未知时先查 GitHub，不能直接标“已取消”或重新合并。异常应覆盖当前实际会启动的验收、审核、仲裁和合并调用，恢复时先核对外部事实，再决定回旧状态或记录完成。只需补上动作编号、尝试编号、任务状态版本和“已发出/结果未知/完成”记录，不必为此另建庞大的分布式系统。
- **严重程度**：中

## 7. 个别“你的决定”缺少回应证据，D 级多家审核也超出了已记录的 C 级决定

- **问题**：ADR 把部分讨论建议写成已接受，并把 C 级的多家审核要求扩到 D 级，现有材料不足以核对这两处转述。
- **证据**：
  - `docs/adr/0001-overall-architecture.md` 评审回应表第 8 条：“接受（Claude × Codex 补充了实现细节）”；但 `docs/adr/reviews/0001-summary.md` 第 8 条“你的回应：”为空，第 10 条也为空。
  - 汇总「新 3」用户回应是“C 级要多家审核都通过”；ADR 的 D 级审查列则写“多家审核 + 你在桌面看完整 diff”。
  - 汇总第 9 条明确记录用户“同意……同时进行的学习任务上限为 3 个”；第 11 条也明确记录“可以，由 Claude 起草”，这些转述有据。
- **建议**：对第 8/10 条标为“讨论建议，待用户确认”，或补上可核对的确认记录；不能从空回应推导接受。D 级是否也必须多家审核，单列请用户确认，未确认前不得拿它卡住 M1。三节 AI 草稿已明确标注，30%、50% 等占位阈值不应指控为伪造决定，但在用户确认前也不能启用。另把草稿“C 级改动你看不到”改为“不逐项批准，仍可查看并按待定方案抽查”，把“换手以后经常凑不齐”改为“可能凑不齐，频率待记录”，避免把流程选择说成访问限制或未测量的频率事实。
- **严重程度**：中

## 8. 七个重新考虑信号尚未定义可观测口径，其中五项需要人工提供事实

- **问题**：信号表给出了阈值，却未定义完整数据来源、样本窗口和归因方法，不能直接作为自动触发器。
- **证据**：`docs/adr/0001-overall-architecture.md`「重新考虑的信号」原列七项如下；`docs/PRD.md` F7 目前只概括为“只追加的事件日志”“理解债账本”，不足以产生这些指标；评审汇总「新 1」仍将 C 抽查方式和初始值列为“待你决定”。
- **建议**：按下表补记录字段与判定口径；自动化负责计算和通知，不能自动撤销用户已定的权限。所有新增阈值、最小样本量及应对动作仍由用户确认。

| 信号原句 | 能否自动测出 | 还需记录或明确什么 |
|---|---|---|
| “后台把 Claude 额度用完，导致白天前台没法用（出现 1 次）” | **只能部分自动**。可记后台限额错误，不能据此证明前台受阻及其原因。 | 前后台会话标识、时间段、调用/消耗记录、额度快照与刷新时间、限额原因；用户确认前台受阻。余额获取能力【未核实】，未知不判未发生。 |
| “无需你介入就完成的任务，连续两周低于 30%，主要原因是凑不齐审核者” | **可在定口径后自动计算**。 | 任务纳入/结束时间、人工介入类型、等待原因/时长、合格审核者集合；按完成周还是入队周统计、未完成任务怎么计、多原因下何谓“主要”。M1 本就人工批准，不能混入成熟多 Agent 流程后误触发重议。 |
| “合并以后才发现的缺陷，每月超过 2 个” | **缺陷认定需人工，计数可自动**。 | 缺陷编号、首次发现时间、关联任务/合并 SHA、确认人、去重/撤销记录；按发现月还是合并月归属。CI 红不自动等于新增产品缺陷。 |
| “你否决 AI 审核意见的地方，事后确认 AI 是对的，占一半以上” | **谁对需证据确认，比例可自动**。 | 否决意见编号、当时 SHA/标准、用户理由、后续证据、谁对及确认时间；分母只含已判定项，待验证/无法判断另列；明确时间窗和最小样本量，防止 1/1 就触发“多数”。 |
| “诱饵测试在 WSL 下有任何一项没挡住” | **预设测试可自动**，测试未执行不等于通过。 | Agent/隔离配置版本、测试目标、预期允许/拒绝、实际结果、执行时间及超时/未执行状态；采用第 5 条区分授权通信与越权出口。 |
| “一个月内，core/ 里由你亲手写的提交占比低于 50%” | **不能只靠 Git 自动认定亲手写**。 | 每项变更的用户/AI/混合贡献声明、参与提供方及统计单位；当前每 PR squash 一提交，提交 author 不能说明原始贡献。“提交占比”也不是学习掌握程度，是否保留此代理指标由用户定。 |
| “理解抽查中‘讲不清’的比例超过 20%” | **答案评价需人工或明确量表，汇总可自动**。 | 抽样总体/方式/入样概率、模块/版本、题目、独立答案、评分依据与确认者、完成时间；定义窗口和最小样本量，没抽查或未作答记未知。C 抽查方案未定前，这项信号没有稳定数据源。 |

  其中“限额致前台受阻、缺陷认定、谁对、亲手贡献、讲不清”五项需要人工输入或验证；系统可自动汇总，不能承诺全自动观测。草稿中“重新考虑 C 级不经过你”等右栏只是复议选项，触发后是否改政策仍须用户决定。
- **严重程度**：中

结论：**改完以下几条后可以定稿**——优先使第 1–5 条形成一致、可执行的流程与权限合同，再对齐异常恢复、确认转述边界并补齐七个信号的观测口径；不需要推翻用户已经作出的架构选择。
