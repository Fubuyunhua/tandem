# ADR-0001 架构评审 · codex

评审日期：2026-11-06。依据：[ADR 草稿](../0001-overall-architecture.md)、[PRD v1.0](../../PRD.md)和[关联学习记录](../../../learn/records/0001-判断与执行分离.md)。以下按严重程度排序；具体场景用于检验设计，不代表已经在当前实现中复现漏洞。本次没有测试本机权限、登录方式或实际额度，涉及这些条件的判断明确标为【未核实】；引用的官方网页均为本日读取的滚动文档。

## 1. Windows 选择可以保留，但“后台只读”没有定义安全边界

- **问题**：问题 2 的 Windows 折中方案只写“只读权限”，没有区分可信 hub 与不可信 Agent，也没有说明由谁在操作系统层强制限制读、写、网络和子进程。
- **为什么重要**：同一日常用户身份下，即使 Agent 不改文件，读取凭据并联网外发也已造成损失；而开发 Agent 若真的完全只读，又无法完成写代码的目标。限制编辑工具并不能限制 shell、MCP 或测试脚本。这里需要逐个运行时核实，而不是一句“Windows 沙箱较弱”：Claude 官方明确原生 Windows 命令不经过其 Bash 沙箱；Codex 官方则提供 Windows 沙箱，并将较新的 Windows 10 支持标为 best effort，不能把两者视作同等隔离能力。[Claude sandbox](https://code.claude.com/docs/en/sandboxing)、[Codex Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)。本机版本、配置及隔离是否实际生效【未核实】。
- **建议**：保留 Windows 原生 hub，但将权限分成两部分：可信控制进程保存 GitHub/飞书凭据；执行 Agent 使用独立非管理员账户、专用工作目录和最小凭据，禁止读取日常账户资料、控制器存储与策略目录，并限制出口。Agent 可以写任务副本，不能写 hub 的运行目录；herdr 是操作界面，不是隔离边界。逐个适配器做一次验收：读取目录外诱饵文件、修改策略、启动子进程、访问未授权地址都应被阻止；只能使用合成秘密。某个 Agent 达不到边界，就只允许人工前台使用或暂不接入无人值守，不能因 Codex 有沙箱就默认 Claude/OpenCode 也安全。独立账户方案较轻，但共享主机仍有残余风险；需要更强边界时可将 worker 放入专用 Windows VM，不必先改变 hub 的部署选择。
- **严重程度**：高

## 2. 决策中心只是计算器，尚未指定真正不可绕过的执行闸门

- **问题**：方案 C 描述了谁算等级，却没有说明谁持有合并、执行、发消息和修改系统的权限，也没有把 GitHub 必需检查接入架构图。
- **为什么重要**：固定代码即使正确地产出“禁止合并”，持有同一高权限 token 的执行器仍可直接合并；反过来，Agent 也可能改写生成 `risk-level` 的代码，让闸门自己报绿。“提示词修改为 D”同样需要独立强制机制。项目又要用自己的流程开发自己：如果运行中的 hub 直接加载 Agent 刚改的本地文件，PR 尚未合并，裁判已经被替换。另一个实际前提是 PRD 选私有仓库，而 GitHub 官方文档列出的私有仓库 rulesets 支持套餐为 Pro/Team/Enterprise Cloud；三份 AI 订阅不能证明这个前提成立。[GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)。当前 GitHub 套餐及规则状态【未核实】。
- **建议**：补一张权限表，逐项列出主体、凭据、可读写资源和禁止动作。把“判断结果”与“执行许可”分开：GitHub 侧可信检查从受保护版本加载策略，以实际 PR diff 和提交 SHA 裁决；worker 不持管理员、合并或修改检查结果的凭据。可信控制器、运行中的发布副本与开发 worktree 分开；更换控制器或策略由人审核并显式部署。将模型、提示词、适配器配置、策略、闸门代码和启动脚本一并纳入保护。M0 必须验证私有仓库规则可用且机器人不能绕过；若套餐或可信检查尚未准备好，就保留人工合并，不宣称自动强制已成立。
- **严重程度**：高

## 3. “可放宽区 + 最多降一级”仍可放宽关键行为，并存在连续降级漏洞

- **问题**：裁决原则没有定义等级基准、动作与路径的优先级、混合改动如何处理，以及放宽是否允许跨事件累积。
- **为什么重要**：“测试”并不天然低风险：删除鉴权回归断言、更新错误快照、修改测试启动脚本，都可能让危险实现通过检查；“文档”也可能是 Agent 会执行的指令或生成器输入。如果 Issue 初次从 D 降到 C，PR 事件再把已降过的 C 当基准降到 B，“每次只降一级”仍然累计降了两级。同一任务拆成多个小 PR，也能掩盖整体影响。因此漏洞不只在于模型是否听话，还在于规则是否对同一对象保持不变量。
- **建议**：定义 `baseline = 所有路径、动作及关联任务规则命中的最高级`，每次都从当前真实改动和受保护策略重新计算，不从上次模型意见继续降。底线项一旦命中不得放宽；未知路径、无法解析、模型超时或意见缺失默认至少 C。放宽需满足规则白名单与固定前提：不能删除/弱化测试，不能改配置、指令文件、可执行脚本或其安全行为；重命名同时检查旧、新路径。记录原等级、候选等级、理由、政策版本和 SHA，并明确同一任务最多一次放宽。用五个反例验收：混合文档与权限代码、测试删断言、重命名进白名单、重复分诊、拆分关联 PR。短期若无法可靠识别，就先只允许普通说明文档放宽，不开放“非核心外围代码”这个模糊类别。
- **严重程度**：高

## 4. 三种消息格式还不是状态机，当前图走不通迟到确认与重启恢复

- **问题**：事件、决定、回执没有定义关联标识、状态转换、失效条件和重复处理语义，而且“你的回答”已进事件采集，通知模块又画了一条收回答的路径，归属不清。
- **为什么重要**：走一个具体场景：Issue 触发任务 T，writer 产出 PR 的 h1；系统发 C 级确认卡；你尚未回复，writer 又推 h2；电脑休眠后恢复，你点击 h1 的同意，随后执行器重试一条旧决定。现有设计没有回答：卡片是否过期、同意作用于哪个提交、是否重复合并、哪个进程保存已执行状态。每一步“只传数据”都能满足，但组合起来仍可能执行未经批准的 h2。回执、通知反馈和日志若再次触发普通分诊，还可能形成无休止的消息循环。
- **建议**：由你定义最小状态机，例如“待处理→运行中→待验证→待人审/可执行→执行中→完成/失败/取消”；把事件标识、任务标识、尝试次数、决定标识、head/base SHA、状态版本、审批对象和有效期写入合同。通知只负责展示与验证回答来源，规范化后的回答统一回事件采集；执行前控制器再次核验当前 SHA 与有效审批。执行器采用幂等键，外部请求超时后先查真实状态再重试；为同一任务加并发互斥。先将待执行命令持久化，再执行并补回执；重启扫描未完成命令并对账，不要求分布式“恰好一次”。把上述场景写成状态转换测试，验证 h1 的确认绝不能批准 h2。
- **严重程度**：高

## 5. Agent 回执被当成事件，却没有划清“自述”和“完成证据”

- **问题**：执行器“收回回执”之后谁验证产物、谁启动另一家审查、谁读取外部 CI 并重新裁决，都没有明确职责。
- **为什么重要**：writer 返回 `verify: 测试通过`、`level: B`，只能证明它这么说，不能证明 GitHub 上当前提交通过。审查意见可能针对旧提交；Agent 进程退出成功，也不代表任务成功。PRD 要求外部 CI 作为完成条件、不同家 AI 写审分离，但 ADR 没把这些要求落实为不可省略的状态与接口；M1 又只接 Claude，若此时就允许自动合并，将提前违反跨厂商审查约束。
- **建议**：把回执分成不可信作者声明与可信证据引用，作者的 `level` 只能是建议。GitHub 适配器获取真实检查结果、来源、完成状态和对应 SHA，审查适配器记录模型提供方、版本、审查 SHA 与未解决问题；决策中心只消费这些结构化快照。执行器负责进程生命周期，调度内核负责选择写/审角色，验证状态转换负责决定证据是否齐全，避免职责悬空。没有第二家可用审查者时排队或由人审，不能让同一个 Agent 换个名称充数；M1 明确仅做 Issue→产物→日志，不开放依赖双 Agent 的自动合并。
- **严重程度**：高

## 6. `git revert` 只撤回代码，红 CI 自动开回滚 PR 还可能永远合不进去

- **问题**：回滚规则把代码历史回退当成系统恢复，却没有定义失败归因、数据副作用、回滚验证和紧急通道。
- **为什么重要**：main CI 变红可能是外部服务、依赖源或偶发测试故障，不一定是最后一次合并；先合并 P1 再合并 P2 后才失败，也不能直接断定 P2 有错。若坏提交破坏 CI，回滚 PR 也可能被同一检查卡住；若理解债或人工审批闸门同样阻断回滚，系统只能等待。代码 revert 也撤不回已执行的数据修改、已发消息或已读取泄露的秘密。简单“相关规则降级”还可能因错误归因惩罚无关类别。
- **建议**：区分“自动生成恢复候选”与“允许自动执行恢复”。记录最后已验证版本、部署/提交关系与副作用；先暂停相关自动派活、保留故障证据，再在干净环境验证 revert 或前向修复。只对已证明可逆、验证通过的限定动作自动恢复；其他走人工处理。设计由人控制、带审计的紧急恢复流程，而不是给 Agent 普遍绕过权限；故障中的安全检查不能默默跳过。对不可逆动作细化到单次操作：备份、恢复演练、幂等约束和执行前确认，而不是只贴 D 标签。信任先暂停，根因确认后再更新对应统计。
- **严重程度**：高

## 7. 额度模块出现得太晚，系统甚至可能在“决定不运行”前先耗掉额度

- **问题**：所有事件先经过模型分诊，额度只是记录模块的一项，尚无调用前预算、审查额度预留、限额后降级和重试上限。
- **为什么重要**：CI 回执、定时器与卡片回答若每次都触发模型，即使没有新开发任务也会消耗订阅；writer 用完剩余额度后，review 无法执行，半成品堆积。PRD 一面说 Claude Pro 最紧、后台应少用，一面在 M1 只接 Claude，MOD-2 到 M3 才上线，顺序冲突。也不能把三家额度合成一个“剩余次数”：Codex 官方说明消耗随任务/模型变化，部分用量共享；Claude 可通过 `/usage` 查看计划使用情况；OpenCode Go 当前按模型定义月度金额及滚动窗口，并提供超额付费开关，PRD 的统一 $12/$30/$60 不能无条件适用于所有模型。[Codex pricing](https://learn.chatgpt.com/docs/pricing)、[Claude costs](https://code.claude.com/docs/en/costs)、[OpenCode Go](https://opencode.ai/v2/docs/console/go/)。本人的实际套餐剩余额度、非交互读取方式与登录有效期【未核实】。
- **建议**：M1 先做简单硬预算，不必等优化模型：规则先处理去重、无关事件和已知安全拒绝，再决定是否调用分诊模型；在派 writer 前预留审查与有限修复额度，同时给白天交互留余量。分别维护提供方/模型的预算、估计误差和刷新时间，额度未知时保守排队，遇限额停止而非紧密重试；禁止未经同意转 API 或超额付费。以一周小规模试跑记录每类任务的分诊、写、审、修复消耗和人工占用，再决定任务并发与“50% 自动完成”目标。区分 Agent 软件与实际模型提供方：不同 CLI 连接同一提供方不满足 PRD 的“不同家”要求。三份订阅是否足够目前不能下肯定结论，最小串行循环可以先做验收，全天后台持续工作则尚无容量证据。
- **严重程度**：高

## 8. “记录只追加”不能自动得到可信、可重放的系统状态

- **问题**：日志、额度、信任和理解债放在一个只追加模块中，却没有说明事实来源、状态投影、版本和更正方法。
- **为什么重要**：同一 CI 失败被重复计数，会让信任无故降低；两个并行任务读取同一份“剩余额度”，会同时把预算花掉。模型更新后，把旧版本成功样本混入新模型也可能错误放权。只保存“模型名称”不能复现原判断，重新调用相同模型也不能保证返回相同意见；只追加更不意味着 Agent 无法伪造、截断或删除本地文件。又因为被降级/放宽的任务抽查率不同，直接把观察到的成功率当总体可靠率会引入选择偏差。
- **建议**：区分原始事件日志与可重建状态视图；额度预留、任务状态使用事务或单写入者协调，日志按事件 ID 去重，更正通过补偿事件表达。每次决定记录输入快照、实际模型意见、策略/提示词/内核版本、状态版本、证据 SHA 和执行结果；回放时使用已保存意见，不再次调用模型。信任样本至少按任务类别、模型/适配器版本分组，并记录抽查概率和抽样来源，供你检验 MOD-1/4 的统计假设。审计日志由可信控制器写入并定期备份，先做实用的权限隔离，不必立即引入复杂防篡改基础设施；禁止把密钥和完整敏感原文写入永久日志。
- **严重程度**：中

## 9. 学习六步只有活动清单，没有保护独立判断与验证掌握的机制

- **问题**：学习模块没有定义触发、先后顺序、验收和积压上限，也未落实 PRD 的“先独立 review，再看 AI 意见”。
- **为什么重要**：若飞书卡片已展示 AI 的结论，人再写“我的猜测”就不再是独立判断；AI 自动生成练习和摘要越快，理解债反而可能积压得越快。“总结只能你写”也无法仅凭文字来源可靠证明，应该设计学习流程，而不是许诺识别人是否用了 AI。PRD 的发现率分母若直接相加双方问题数，会重复计数共同发现，且把 AI 误报也计为真问题，指标可能奖励无效找茬。
- **建议**：为 C/D review 保存未展示 AI 意见时的人类答案版本，提交后再解锁对照；手机通知先只给风险事实与待决选项，不提前泄露审查结论。六步记录增加问题来源、待确认共性、练习答案、人的总结、复习日期与验收状态；已确认学会至少用一次延迟解释或迁移题验证。按每周可投入时间限制学习在途数量，积压过多时减慢新任务，而非自动判定掌握。问题清单先去重、确认有效，再以有效问题集合的并集作发现率分母，另记误报；它仍不是对所有真实缺陷的召回率。找茬题只能在隔离练习副本使用，不能进入真实 PR；紧急恢复与常规学习验收分开。
- **严重程度**：中

## 10. ADR 仍同时承载互相冲突的选择，没有可验收的暂定决定

- **问题**：“决定／代价／重新考虑的信号”全部空白，Windows 倾向与“M1 再迁移 WSL”的折中、PRD 的 M1 在 WSL 运行还没有形成一致基线。
- **为什么重要**：执笔人觉得“先 Windows”已经定了，实现者却可能按 PRD 直接做 WSL hub，另一个人按折中方案做临时只读版本；这些都能声称遵守文档。问题 1 的“已基本达成一致”也不能代替明确的 v1 责任边界。还有两个备选理由过强：“纯规则写不出语义判断”应改成规则难以穷尽且维护成本高；“云端天然隔离”不能省略网络、凭据与挂载配置，否则比较本身就带偏决策。
- **建议**：由你在评审后亲写一句可执行决定，例如“v1 hub 在 Windows 原生运行，worker 达到隔离验收才无人值守；M1 不自动迁移；未验收的适配器仅前台使用”，并说明适用阶段和不承诺的能力。将后续 PRD 同步列为待办，本次评审不替你修改。重新考虑的信号应可观测：隔离验收失败、休眠重启后无法恢复、周额度不够完成已承诺审查、GitHub 侧闸门不可用等；对应后果分别是停用 worker、修恢复机制、缩减任务或重议运行位置。标明哪些细节留待 ADR-002/003，哪些是本 ADR 必须守住的不变量，避免总体架构变成无限细化的实施说明。
- **严重程度**：中

## 三句话总结

这份 ADR 最大的优点是把模型意见与固定代码裁决分开，并把人的建模和判断练习保留为架构目标。
最大的风险是把逻辑分层误当成权限隔离，导致 Agent、执行器或新开发代码能触及裁判和凭据，使正确裁决也无法约束真实动作。
定稿前必须补上一份“谁持有什么权限、决定绑定哪个提交、谁验证后执行”的端到端合同，并用迟到确认、重复事件和策略自修改三个反例验收。
