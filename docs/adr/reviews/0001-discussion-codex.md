# ADR-0001 第 8–11 条讨论回应 · codex

日期：2026-11-06。已读讨论任务书、评审汇总、任务状态流转、当前 ADR 和 PRD；状态流转以**第六版**为准，旧版本只用于理解讨论过程。

本文是交给 Claude 与用户讨论的意见，未代用户定稿。已确认的 WSL2、C 级不经用户批准、用户可否决 AI 意见但需逐条写理由、CI 不能越过、调度器暂缓等决定，都作为现有约束；下面的补充与取舍仍须用户决定。

## 第 8 条：重放与统计偏差

**同意方向；补充实现边界；反对把“保存抽查比例”理解为已经解决统计偏差。**

### 重放应恢复事实，不重新执行历史动作

同意由日志恢复当前状态，状态转换写成纯函数；也同意保存当时输入与模型意见，重放时不再调用模型。但要区分两种用途：

- **恢复运行状态**：按已记录的事实还原，不重新发通知、启动 Agent 或合并 PR。已经生成的动作需有动作编号和执行回执，重启后只对未确认完成的动作查证、补执行。
- **检验新规则**：拿历史输入和旧模型意见运行新版本，输出影子结果并与原决定比较，不改变原日志，也不自动产生真实副作用。

例如历史记录说“请求合并 h1”，hub 在收到成功回执前崩溃，重放不能直接再次合并；外壳应先查 GitHub 上 PR 的真实状态。只还原任务状态但不记录动作是否完成，仍会留下重复执行窗口。

建议每次决定至少关联：事件编号、任务/尝试编号、事件顺序、实际输入快照、模型原始意见与解析结果、策略/提示词/内核版本、目标 SHA、生成动作及后续回执。模型版本无法精确取得时记录可取得的标识并注明未知，不能宣称以后可重现同一次模型生成。

### 快照要先定义可保存内容，再谈密钥扫描

同意敏感文本不进 Git，也支持 `data/` 作为候选目录；但 `.gitignore` 只关系到 Git 收录，不限制其他进程读取，也不阻止备份、日志和模型请求泄露。当前 `data/` 的忽略与访问权限配置【未核实】。

建议输入只保留决策所需字段，在持久化和发送模型前统一脱敏，并扫描模型输出；扫描未命中不能当成“没有秘密”的证明。要记录**模型实际收到的脱敏版本**，不能模型读的是原文、日志存的是另一份文本却声称可重放。确认发现秘密时，倾向于隔离该输入、停止传播并通知用户处理，而非为了“保存原话”永久保留密钥。

“只追加”应约束正常业务更正，不能默认为秘密泄露后也永不允许清理。脱敏规则、保存期限、谁能读，以及安全清理是否作为例外，都列为待用户决定。

### 记录的是实际入样概率，不只是配置中的百分比

同意按任务类别和模型版本分组，但还应保留未抽中任务的清单、当次抽样规则、实际入样概率和检查结果是否完成。某类按 30% 随机抽，另一类因分歧必查，就不能都写成 30%；若用户只挑“看起来有问题”的项，单靠配置比例无法事后修正。

逆概率加权有前提：目标总体中各项要有已知、非零的入样概率；某类永不抽查，权重无法补出其未知结果。统计依据见 Changbao Wu 的[讨论论文](https://www150.statcan.gc.ca/n1/pub/12-001-x/2024001/article/00002-eng.pdf)（Statistics Canada，2024-06-25）。这是方法前提，不是对本项目估计器已有效的证明。

建议将“随机审计样本”“分歧必查样本”“事后暴露缺陷”分别标记；没有完成检查的项不计作成功。先保存数据，MOD-1/4 再由用户决定估计目标和模型；不要把加权样本直接当成普通独立成功/失败次数塞入 Beta 后验，然后沿用原来的置信解释。

## 第 9 条：学习模块

**同意独立答案保护、评审记录和标签匹配；部分反对将每项学习产出强制变成规则或提示词修改。**

### 独立判断需要控制所有展示入口

同意先保存用户答案再展示 AI 意见，并由外壳执行。不过遮住桌面面板还不够：飞书摘要、通知标题和自动生成的讲解也不应提前泄露结论。建议以任务与 SHA 标记“独立答案已提交/AI 意见已展示”；如果用户早已在 GitHub 看过意见，允许继续评审，但这份记录标为“非独立”，不混入独立发现率。

这是保护练习条件，不是监控用户，也不应阻止用户使用已经确认的最终决定权。紧急人工处理是否跳过练习、跳过后如何计分，留给用户选择。

### 学习回流应允许“不改生产规则”

学懂分层、发现一次误报，可能只需总结或复习，不一定需要改规则。若强制每条学习都产出 D 级变更，会把学习任务变成规则膨胀和审核负担。

我的提议是：学习可以产出知识记录、复习任务、测试建议或规则/提示词修改提案；**只有实际修改受保护规则或提示词时才走 D 级**。提案并不自动生效，也不由学习模块直接写入运行配置。Claude 提出的“同时进行最多 3 个”可以作为候选初值，但任务书并未记录用户已批准这个数字；还要明确它限制的是正在练习的任务，不是问题历史，也不意味着第 4 个问题被丢弃。

### 标签匹配放在纯函数，查询与提醒放在外壳

同意用标签做 v1 同类匹配，足够简单且可解释。建议由外壳取当前任务标签与已保存学习记录，内核算出匹配项及提醒动作，外壳展示；内核不自己查数据库或发卡片。标签来自人或模型都应注明来源，模型新增标签不能自动改变权限或风险等级。是否去重提醒、多久不再打扰、哪些标签由人确认，尚待用户决定。

### 去重并集还要剔除误报，并允许暂时不知道谁对

同意用双方发现的去重并集作分母，但应先确认问题有效。设用户独立发现的有效问题为 H，AI 发现的有效问题为 M，可记录 `|H| / |H∪M|`；并集为空时记“不适用”，而不是 100%。它只是“相对于已知有效问题的发现比例”，不表示所有真实缺陷的召回率。

“否决 AI 时逐条写理由”是用户已定的机制，我支持纳入评审记录；**合并后没出事不能自动证明用户对，AI 坚持意见也不能自动证明 AI 对**。每项至少保留问题编号、双方原话、当时证据、用户理由、对应 SHA/标准版本、后续证据和“已确认/待验证/无法判断”。这既保留用户决定权，也避免模型充当自己正确性的裁判。

新增评审记录格式后，原 ADR 的“只通过三种格式通信”要同步调整；格式最终字段仍由用户设计。

## 第 10 条：图纸箭头方向与内核签名

**同意明确内核输入输出；反对“记录 → 决策中心这条数据箭头本身就违反依赖方向”的推论；补充状态与执行边界。**

外壳把已读好的数据传给纯函数是合法的：`state = load()` 在外壳执行，再调用 `decide(state, ...)`，内核没有因此读取外壳。真正违规的是内核自己调用存储、时钟、GitHub 或模型接口。数据流向、函数调用方向、代码依赖方向应分别标清，不能靠删箭头教出“内核不能接收外部数据”的错误理解。

可以删掉含糊箭头，但建议把图改写成明确的数据路径：

```text
存储/GitHub/时钟 → 外壳读取并组织快照 → 内核纯函数
内核返回新状态与动作 → 外壳持久化 → 外壳执行动作
执行结果 → 新事件 → 下一次状态转换
```

Claude 提出的签名方向合理，但只是候选：

```text
decide(任务当前状态, 事件, 策略, 额度快照, 信任快照, 当前时间)
    → (新状态, 动作清单)
```

补充四点供用户定接口时考虑：

1. **策略不一定只有 `risk.yml`。** 如果 `risk.yml` 仅存路径映射，审核标准版本、各状态允许动作、重试上限和权限约束还需要明确归属；若全部放进该文件，就说明其 schema。不能把文件名当作已定义完整的策略合同。
2. **“任务当前状态”应是任务记录，不只是状态名。** 第六版所需的方案批准范围、写手历史、提交/标准版本、计数、原因都要能输入；影响决定的证据和全局额度也不能藏在未声明的可变变量里。
3. **顺序和抽样也需要显式输入。** 同一任务的事件要按持久化顺序处理，拒绝旧状态版本上的决定。若内核负责抽样，将随机抽签值或可重放种子作为输入并记日志，不在函数里取隐式随机数；历史重放不再次生成真实动作。
4. **第六版的布尔批准标记不够表达批准对象。** “方案已批准”宜关联方案版本/范围；执行许可关联 SHA、审核标准和证据。新代码、改标准或取消事件到达后如何使旧许可失效，应在转换条件写清。外壳接到动作后还要核验许可有效，不能只因先前曾到“待合并”就执行。

用户已暂缓调度器，我不据此要求现在新增调度模块。v1 可以在现有决策中心使用明确快照；是否拆成“状态恢复函数”和“动作决策函数”，由用户衡量学习成本与实现复杂度。

## 第 11 条：文档矛盾

**同意修正绝对说法与整理历史；补充“已决定”与“已验收”不能混写，AI 草稿也不能代替用户立场。**

确认问题 2 已改为 WSL2，不再讨论它是否仍应选 Windows。赞同将两句改成“规则难以穷尽，维护成本高”和“隔离取决于配置”；“当时没有写清具体文件管理问题”可以作为决策过程的复盘，而不是补造用户当时的理由。

不过，当前 ADR 的备选段仍保留旧绝对说法、“Windows 到 M1 再迁 WSL”的折中，以及未填的决定段；PRD 仍写 `core/` 由用户编写、C/D 每项先人审，也落后于后续决定。这些应由后续文档整理一次同步，不让实现者自行挑选有利版本。本次只记录，不修改它们。

Claude 起草“决定/代价/重新考虑信号”可以接受，但请明确标成“AI 草稿，待用户改写确认”。既有决定可以准确转述；新的额度阈值、抽查率、保留期限、暂停条件不能混进“已决定”。WSL2 是选定位置，诱饵测试、凭据隔离和睡眠恢复则是验收项；尚未在本机验证的能力仍为【未核实】，不能写成“选择 WSL 后 AI 就碰不到个人资料”。

## 新问题（最多 3 条）

### 1. C 级自动合并已经确定，但“理解债”采样还没有能执行的定义

**不是要求恢复逐 PR 批准。** 风险在于 ADR 对 C 级写“不用看、抽查待定”，而 PRD 又以讲清模块和独立评审为目标；如果实现把“待定”当成 0，就既没有抽样数据，也没有理解债的观测来源。这里应区分“有缺陷吗”的质量抽查与“用户讲得清吗”的理解练习，两者可以抽同一项，但不能互相代替。

**提议与取舍：** 可选择合并后每日固定数量，简单且符合注意力预算；也可采用非零分层随机比例，便于估计各类风险，但工作量会随产出变化。两者都保留 C 自动合并；只有被抽中的练习才要求先写独立答案。PRD 的 `comprehension` 检查究竟只是检查证据记录，还是会阻断所有 C 合并，也需明确，否则会暗中把人审加回来。抽样方式、初值与积压后减慢派活的阈值均待用户决定，不能由我们替用户填百分比。

### 2. 保留用户否决权后，需要避免把“人工最终负责”误实现成“作者身份即可免审”

用户已决定可以批准自己的代码，我接受：这把 AI 审查定位成必须收到并回应的意见，而不是 AI 对用户的否决权。`core/` 的保护因此变成“强制参与、CI 与留痕”，不再是“必须人机一致”；这是有意识的取舍，不应假装仍然要求双方同意。

新风险是额度交接或“让 AI 帮我改”后，一次任务里会同时有用户和多个 AI 作者，系统只存“最后写手是谁”就可能遗漏参与者；若再用 Git author 字段决定是否允许覆盖 AI 意见，也未必符合实际参与情况。应由用户在受验证的入口显式作出“我承担这份改动并否决这些意见”的决定，而非作者字段自动触发放行。

**建议候选约束：** 所有实际写过代码的 AI 提供方保留在任务历史，不能被换手清掉；人工否决绑定当前 SHA 与标准版本，逐条列理由，新提交后重新审核/确认；CI 要求不变。“用户自己写的代码”与“AI 写、用户接手”的否决权限是否相同、如何声明混合贡献，待用户划界。未复现的争议保留未知状态，不用事后安静运行充当用户正确的证明。

### 3. 三份订阅可接入第三家模型，但交接后可能耗尽合格的角色

**官方核查结果：** OpenCode Go 当前文档列出 GLM-5.3、GLM-5.3-Flash、Kimi、MiniMax、Qwen、DeepSeek 等模型，也列有 GPT 与 Claude 系列；所以“用了 OpenCode Go”本身不能证明独立。可以核实的具体候选是 **Go 中的 GLM-5.3**，Z.ai 官方明确它是自己的模型，因此按当前“模型提供方不同”的意图，它可以作为区别于 OpenAI/Anthropic 的第三家。[OpenCode Go](https://opencode.ai/v2/docs/console/go/)、[Z.ai GLM-5.3](https://docs.z.ai/guides/llm/glm-5.3)（2026-11-06 读取的滚动文档）。OpenAI-compatible 接口是协议形式，不会把 GLM 变成 OpenAI 模型。官方可选不等于本人账户已配置可用：本人的访问权限、剩余额度和适配器调用均【未核实】。

**具体走查：** Claude 写到一半额度用完，Codex 接着写；遵守“写过代码就不能审”，Anthropic 与 OpenAI 都在写手历史里。GLM 可以审，但若作者拒绝修改，GLM 又不能仲裁自己的审查，前三家中已无合格仲裁者。第六版第 17 条的 R03→待你介入已经给出合法出口，因此这不是必然死锁，但会降低自动完成率。若 C 级还要求两家审核者，而不是一家主审加分歧仲裁，角色不足会更早发生。

**提议与取舍：** 不恢复已经暂缓的复杂调度器，也不要求每任务预留额度；先维护写手提供方集合、审查者与仲裁者资格，开工/交接时展示还能组成哪些角色。可以接受换手后人工兜底，最省实现成本；也可优先等待原写手额度重置以保存独立角色，但延迟更长；Go 内另选不同家族的模型也可能补角色，但须核实其归属、当前可用性与审查质量。用户需决定 C 是“一家独立主审，分歧再第三方仲裁”还是“多家审核通过”；GPT 写代码时不得硬指定 GPT 同时充当独立审核者。三份订阅不等于只能有三家模型，也不保证任何时候都有足够合格角色。
