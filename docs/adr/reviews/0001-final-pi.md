## 1. M1 在第六版状态机里根本走不通：派活条件永不满足，且没有"你批准 B/C 级"的状态

- **问题**：状态流转第六版只覆盖"写手 + 审核者（至少两家模型提供方）"的世界，没有为 M1（只接 Claude、由你审）建模，两条硬规则直接把 M1 卡死。
- **证据**：
  - `docs/design/task-lifecycle.md` 第六版 #1：「待处理 → 处理中 | 派活 | **写代码的 Agent 和至少一家审核者有额度**」。M1 只有 Claude 一家（且它是写手），"至少一家审核者有额度"永远为假 → 没有任何任务能离开"待处理"。
  - 同文件 #12/#13：「待AI审核 → 待合并 | 审核通过 | 不是 D 级」「待AI审核 → 待你审核 | 审核通过 | D 级」，而状态清单写「待你审核 | **只有 D 级才有**：等你批准」。
  - `docs/adr/0001-overall-architecture.md` 等级→流程表：「只有一家可用时（例如 M1 只有 Claude）……**B、C 级都改为由你批准**」。
  - `docs/PRD.md` M1：「只接一个 Agent（Claude），**所以 B、C 级也由你批准**」。
- **建议**：要么给第六版加 M1 专用条件（#1 改为"写手有额度，且（有审核者额度 **或 本轮由你审**）"），要么新增"待你审核（B/C 级，M1）"的显式转换，并明确 M1 阶段非 D 级审核通过后进入"待你审核"而不是"待合并"。这条不补，M1 的范围描述和状态机就是两份互相矛盾的文件，实现者无论照哪份做都会被另一份判为错。
- **严重程度**：高

## 2. "C 级要多家审核都通过"在状态机里没有对应机制

- **问题**：ADR 定了"C 级多家审核都通过"，但第六版转换表删掉了第五版的"换一家继续审"，只剩"一家审核、不通过就退回修改"一条路径，"多家"如何汇聚、谁算"都通过"、改一版后已通过的那几家要不要重审，全部没有表示。
- **证据**：
  - `docs/adr/0001-overall-architecture.md` C 级行：「审查 | **多家审核者都要通过**（你的决定）」。
  - `docs/adr/reviews/0001-summary.md` 新3 你的回应：「**C 级要多家审核都通过**。不用 GLM」。
  - `docs/design/task-lifecycle.md` 第五版 #10：「待AI审核 → 待AI审核 | 审核不通过 | 还有没审过的审核者，换一家审（**待确认，见问题 1**）」——这一条在第六版被删除。
  - 第六版只剩 #14「待AI审核 → 待处理 | 审核不通过，退回修改」、#14b、#15（修改次数达 3 次→待你介入），没有任何"多名审核者各自的通过/未通过如何合并"的转换或状态字段。
- **建议**：在"待AI审核"上挂一个字段"已通过的审核者名单 + 每家的审核标准版本"，并定义：任意一家不通过 → 退回修改（#14）且该任务回到"待验收"时**所有审核者的结论作废重审**；只有"名单包含全部指定审核者且都通过"才触发 #12/#13。或者退回"一家主审、分歧再仲裁"并同步改 ADR。两者选一，不能像现在这样 ADR 说多家、状态机说单家。
- **严重程度**：高

## 3. 回执合同缺"提交编号"字段，而状态机把它当硬条件

- **问题**：三种"合同"之一（回执）没有定义提交编号，但状态流转至少三处把"回执带提交编号""提交编号一致"作为转换的前置条件。合同由你定义，现在这个字段处于"既没写进协议、又被状态机依赖"的悬空状态。
- **证据**：
  - `docs/PRD.md` F4 回执协议：字段只有 `ask/notice/later` 和 `brief{what/why/verify/rollback/learn/level}`，**没有提交编号（SHA）**。
  - `docs/design/task-lifecycle.md` 第六版 #2「交回代码（**回执带提交编号**）」、#9「CI 绿 | **和回执的提交编号一致**」、#20「合并成功 | **提交编号和审核时一致**」。
- **建议**：把提交编号（以及任务编号、第几次尝试）写进回执协议和"任务记录"合同，作为必填字段；否则 M1"实现回执解析"时没有解析目标，第 9、20 条的校验也无从谈起。
- **严重程度**：高

## 4. "发布/对外发送"由执行器识别动作类型，等于把底线交给 AI 写的外壳；且与"打标签→A"措辞冲突

- **问题**：底线条目表把"发布/对外发送"这类**运行时动作**和"路径命中"这类**静态 diff 判定**混在同一张表里，前者的判定方式写的是"由执行器识别动作类型"。执行器是外壳、是 AI 写的——这正好把整份 ADR 想消灭的"askFirst 只是软约束"以另一种形式请了回来：判断一件事是不是"对外发送"的代码，本身可以被改。
- **证据**：
  - `docs/adr/0001-overall-architecture.md` 底线条目表：「动作 | 发布或对外发送：打 tag、发 release、发包、给外部发消息 | **由执行器识别动作类型**」。
  - 同文基础级别第 1 步：「**不改仓库的动作（打标签、写评论、生成报告）→ A**」——"打标签"（label）与上表"打 tag"（git tag）极易混读，且"打 tag"是否属于"不改仓库的动作"没有澄清，同一动作可能在 A 与 D 之间漂移。
  - 同文裁决原则：「**底线由固定规则守住**」「哪些属于可放宽区由规则划定，**不由模型判断**」。
  - 附带张力：拆 PR 规则「同一个 Issue 产生的多个 PR，按合计改动算级别」与"每次都根据真实改动（即本次 diff）重新算级别""放行绑定提交编号（单个 SHA）"冲突——跨 PR 合计无法由单个 SHA 表达，需要额外的 Issue→PR 归属与历史合计机制，文档未写。
- **建议**：把"发布/对外发送"从 diff 分级里拆出去，作为**执行器工具层的硬拦截**（类似 Claude 的 PreToolUse hook / 网络白名单 / 分支保护那样的机制，且拦截代码属于 `core/` 或受保护的 `scripts/gate/**`），而不是靠执行器"识别"。同时把"打标签/打 tag"统一成明确术语，并写明"拆 PR 合计"的归属关系存在哪里、按哪个版本合计。
- **严重程度**：高

## 5. 四份文件在 `core/` 审核口径上不一致："必须双方同意" vs "你有权直接批准自己的代码"

- **问题**：汇总里你第 3 条的回应写的是"必须双方同意"，但 ADR、状态流转（你的原话）和新 2 都指向"你保留最终决定权、可以直接批准自己的代码"。汇总的问题 3 单元格没有被同步修正，成了四份文件里唯一还在说"双方同意"的地方。
- **证据**：
  - `docs/adr/reviews/0001-summary.md` 第 3 条你的回应：「AI 改的要你同意才能合并，你写的要 AI 审查。**必须双方同意**，而且你必须参与」。
  - `docs/adr/0001-overall-architecture.md` `core/` 审核规则：「你改的：必须经过 AI 审核，但**你有权直接批准自己的代码**……不能否决你」。
  - `docs/design/task-lifecycle.md` 场景 9 你的原话：「**我自己的代码我有权利直接批准**」。
  - `docs/adr/reviews/0001-summary.md` 新 2：「以后不要再说成『双方同意』」。
  - 另需你确认的一处：ADR 问题 2 标为"你的原话"的「既然考虑到安全性，那么还是使用 WSL 方案更好」，在汇总第 1 条的原话里找不到这一句（汇总写的是"接受，并改为 WSL2，理由是安全性"）。如果这不是你的原句，应改标注为 AI 转述。
- **建议**：把汇总第 3 条的"必须双方同意"改为与新 2 一致的口径（AI 改→你批准；你改→AI 审但你保留最终决定权，否决要逐条留理由并绑定提交编号/标准版本）。并核实 WSL2 那句引文的原始出处，不是原话就降级为转述。
- **严重程度**：中

## 6. "C 级不用看"与"理解债靠抽查"没有闭环，抽查方式仍是待定

- **问题**：ADR 一面说 C 级"你要看什么＝不用看"、通知走日报，一面说理解债只能靠抽查发现，而抽查方式与初始值始终"待定"。PRD 4.3 却已承诺"被抽中的 C 级 PR 你先独立 review"，三者连不成一条可执行的链。
- **证据**：
  - `docs/adr/0001-overall-architecture.md` 等级→流程表 C 级：「你要看什么 | 不用看」「抽查（初始值）| **待定（见'待你决定'）**」；代价节「**C 级改动你看不到。理解债只能靠抽查来发现，抽查方式还没定**」。
  - `docs/PRD.md` 4.3：「每个 D 级 PR 和**被抽中的 C 级 PR**，你先独立 review」。
  - `docs/adr/reviews/0001-summary.md` 新 1：「抽查方式：每天固定抽几个还是按比例抽？**初始值是多少？**」——无你的回答。
- **建议**：定稿前把"待定"落成一个可运行的初始值（哪怕只是"每天固定抽 1 个 C 级，满 2 周再调"），并明确抽查事件在状态机里的位置（合并后触发、由定时器/记录模块产生）。否则 PRD 4.3 和成功标准里"讲得清 ≥80%"从第一天起就没有数据来源。
- **严重程度**：中

## 7. "重新考虑的信号"多数不能自动测出来，缺数据字段与登记流程

- **问题**：信号表本身是好的，但逐条看，大多没有对应的自动采集点；现在直接定稿，这些信号要么测不出、要么触发条件是空集。
- **证据与所需数据**（信号表在 `docs/adr/0001-overall-architecture.md`「重新考虑的信号」）：
  - 「后台把 Claude 额度用完，导致白天前台没法用（出现 1 次）」：需要记录①额度耗尽事件（M1 已在记）②"白天前台被拒"事件——后者目前没有任何来源，需要你/herdr 报一条"前台交互被限流"。
  - 「合并后才发现的缺陷，每月超过 2 个」：需要一条"漏检登记"流程（谁、在哪个 PR 事后发现问题并标记为漏检）；PRD 成功标准有"漏检每月 ≤2"却没有任何登记机制，此信号测不出。
  - 「你否决 AI 审核意见，事后确认 AI 对，占一半以上」：需要事后判定（已确认/待验证/无法判断）的录入动作；ADR 只写了"以后复盘时统计"，没写谁在什么时候录入。
  - 「一个月内 `core/` 里由你亲手写的提交占比低于 50%」：需要 git author 归属约定——AI 用机器人账号提交、你用本人账号？现在没有约定，"亲手写的提交"无法自动统计。
  - 「理解抽查中'讲不清'比例超过 20%」：依赖第 6 条的抽查机制，抽查不定，此信号无输入。
- **建议**：给每条信号补一个"数据从哪来"列；缺的补进记录模块的字段或新增登记流程（漏检登记、前台被拒、否决事后判定、core 提交作者约定）。否则"重新考虑的信号"这一节会变成只能在复盘时靠记忆手工判断，失去自动触发的作用。
- **严重程度**：中

## 8. M1 里 D 级的"多家审核"无法满足，且诱饵测试是 M1 的前置条件但未写失败回退

- **问题**：D 级流程要求"多家审核"，但 M1 只有 Claude（且是写手不能自审），D 级实际只剩你一道把关；ADR 只在"只有一家可用时"那段处理了 B/C，没处理 D。另外"每家 Agent 通过诱饵测试后才允许无人值守"是 M1 的开工前提，但诱饵测试和"关闭 automount/interop 后 Agent 能否工作"都是未验证的验收项，ADR 没写"没过怎么办"。
- **证据**：
  - `docs/adr/0001-overall-architecture.md` D 级行：「审查 | **多家审核 + 你在桌面看完整 diff**」；同文「只有一家可用时（例如 M1 只有 Claude）……B、C 级都改为由你批准」——未提 D 级。
  - 同文「决定」：「每家 Agent 通过诱饵测试后，才允许无人值守运行」；验收项「WSL 关闭 automount 和 interop 之后，各家 Agent 能否正常工作」【未核实】。
  - `docs/PRD.md` M1：「只接一个 Agent（Claude）」。
- **建议**：补一句 M1 的 D 级实际执行方式（你批准方案 + 你批准合并，AI 审核缺位时明确"无 AI 审"并在记录中标注），并给诱饵测试写一个失败分支（没过→Agent 只在前台 herdr 用，M1 的无人值守部分顺延或改用 Codex 前台跑）。这属于把"已决定≠已验证"里的验证项与 M1 计划对齐。
- **严重程度**：低
