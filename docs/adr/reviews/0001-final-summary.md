## 一、三家都提到的问题

### 1.【高】M1 在状态流转里走不通（三家都提）
- **问题**：
  - 第 1 条转换的派活条件是"写手**和至少一家审核者**有额度"。但 M1 只有 Claude 一家，它又是写手，所以这个条件永远不成立，任何任务都派不出去。
  - ADR 和 PRD 都写了"M1 阶段 B、C 级由你批准"，但状态流转里没有这条路：非 D 级任务审核通过后直接进入"待合并"。
  - D 级要求"多家审核"，M1 也满足不了。
- **Claude 的意见**：【照改】增加一个"运行模式"：单 Agent 模式（M1）和多 Agent 模式。单 Agent 模式下：
  - 派活时只检查写手有没有额度；
  - CI 变绿后，所有等级都进入"待你审核"；
  - D 级照样要你先批准方案，记录里标明"这次没有 AI 审核"。
- 另外，pi 提出**诱饵测试没通过怎么办**还没写。建议：没通过的那家 Agent 只在前台 herdr 里用，不进后台。【照改】

### 2.【高】"C 级多家审核都通过"在状态流转里没有体现（三家都提）
- **问题**：第六版删掉了"换一家继续审"，现在只要**一家**审核通过，任务就进入"待合并"。仲裁那条线（第 16 条）甚至能在原审核者反对的情况下直接放行。
- **Claude 的意见**：【待你决定】这里有三个问题必须由你来定：
  1. **"多家"至少几家？** 建议 2 家，并且两家要来自不同的模型提供方，也都不能是写手。
  2. **有一家不通过，代码退回修改。改完以后，之前已经通过的那一家要不要重新审？** 建议重新审，因为代码变了，之前的"通过"是针对旧代码的。
  3. **仲裁还保留吗？** 在"多家都要通过"的规则下，仲裁者说"写手是对的"，算不算推翻了那一家的反对？
     - A. 仲裁可以推翻某一家的反对；
     - B. 取消仲裁：写手拒绝修改时，直接进入"待你介入"。
     - Claude 倾向 **B**，规则更简单，你又说过"都有问题再找我"。

### 3.【中】"重新考虑的信号"大多测不出来（三家都提）
- **问题**：七条信号里，有五条需要人来提供事实，系统自己无法判断：
  - 前台额度是不是因为后台被用完；
  - 某个缺陷是不是合并之后才发现的；
  - 你否决的地方后来证明谁对；
  - `core/` 里的代码是不是你亲手写的；
  - 理解抽查时你是不是"讲不清"。
- **Claude 的意见**：【照改】给信号表加一列"数据从哪来"，需要人工的就配一个登记方式，比如：
  - 合并后发现的缺陷，在 Issue 上打 `escaped-bug` 标签，并关联原来的 PR；
  - 前台额度用完时，在手机上点一下"报障"；
  - 你否决 AI 的地方，复盘时录入"已确认 / 待验证 / 无法判断"；
  - 提交时声明这次改动是你写的、AI 写的，还是混合的。
  - 另外，每条信号都要有最小样本量，防止"1 次里错 1 次"就触发"一半以上"。
  - 具体的阈值仍然等你定。

## 二、两家提到的问题

### 4.【高】"不改仓库的动作 → A 级"会吞掉"对外发送 → D 级"（Codex、pi）
- **问题**：
  - 基础级别的算法第一步是"不改仓库的动作 → A"，但"给外部发消息"也不改仓库，于是被判成了 A。这和"只要命中底线条目就是 D"矛盾。
  - "打标签"（给 Issue 加 label）和"打 tag"（给 git 提交打版本号）的说法容易混淆。
  - pi 还指出："对外发送"写的是"由执行器识别"，可执行器是 AI 写的外壳，等于把底线交给了 AI。
- **Claude 的意见**：【照改】
  - 算法改为**先检查底线条目，再看是不是 A 级**；
  - 统一用词："加 label"属于 A，"打 git tag"属于 D；
  - 发布和对外发送改在工具层**硬拦截**，比如设置网络白名单、禁止 Agent 拿到发布权限，拦截代码放在受保护的目录里，而不是靠执行器去"识别"。

### 5.【中】"C 级不用看"和"理解抽查"还连不起来（pi、Codex）
- **问题**：C 级的抽查方式一直是"待定"。如果实现时把"待定"当成 0，你就永远看不到 C 级的改动。PRD 里"讲得清 ≥ 80%"这个目标也就没有数据来源了。
- **Claude 的意见**：【待你决定】pi 的建议是"**每天固定抽 1 个 C 级，两周后再调**"，我同意，因为简单，你每天的工作量也固定。你来定方式和初始值。

### 6.【低】评审第 8、10 条你其实没有回应过（Codex、agy）
- **问题**：ADR 的回应表里写着第 8 条"接受"，但你只说过"剩下的你先和 gpt 讨论一下"，没有对第 8、10 条表过态。这是我转述过头了。
- **Claude 的意见**：【待你决定】请确认第 8 条（重放和统计）和第 10 条（Codex 纠正了箭头那条评审）你是否接受。

## 三、只有一家提到，但 Claude 认为成立的问题

### 7.【高】你是写手时，被 AI 打回后无法直接批准（agy）
- **问题**：第 14b 条：你的代码被 AI 审核打回后，任务进入"你处理中"，但"你处理中"只能走向"重新提交"。你保留的"直接批准自己代码"的权力，在状态流转里没有出口。
- **Claude 的意见**：【照改】你是写手时，被打回后改为进入"**待你介入**"，并带上 AI 的反对意见。你在这里可以选：
  - 修改：进入"你处理中"；
  - 直接批准：逐条写理由，而且 CI 必须是绿的，然后进入"待合并"。

### 8.【高】回执里没有"提交编号"这个字段（pi）
- **问题**：状态流转有三处要核对提交编号，但 PRD 的回执格式里没有这个字段。
- **Claude 的意见**：【照改】回执增加三个必填字段：任务编号、第几次尝试、提交编号。

### 9.【高】批准要绑定版本，改动过程中级别可能升高（Codex）
- **问题**：
  - "方案已批准"只是一个是或否的标记，没有记录批准的是哪个版本的方案。
  - 有新提交进来以后，哪些审核结论作废，没有写。
  - 一个 C 级的"改样式"任务实际上改了依赖文件，应该升成 D 级，但状态流转里没有这条路。
- **Claude 的意见**：【照改】
  - 每次收到回执，都根据真实改动重新计算级别。如果升成了 D 级、方案又还没批准，任务就进入"待你批准方案"。
  - 批准记录绑定方案版本；审核结论绑定提交编号。有新提交进来，审核结论全部作废。

### 10.【高】诱饵测试的写法太绝对，凭据归属没写（Codex）
- **问题**：
  - "访问外网要被挡住"写得太死。Agent 本来就要联网，才能调用模型、访问 GitHub。
  - "不许改 `risk.yml`"和"改 `risk.yml` 按 D 级处理"字面上冲突：前者指正在生效的那份配置，后者指代码仓库里的那份。
  - 谁持有哪些凭据也没写清楚：后台服务、Agent、合并组件各自有什么权限。
- **Claude 的意见**：【照改】
  - 诱饵测试改为三条：禁止读取私人密钥、禁止改动正在生效的配置、禁止访问白名单以外的地址；同时要验证允许的通信能正常进行。
  - 凭据清单放到 M1 开工前，单独写一份文档。

### 11.【中】异常和取消的规则不统一（Codex）
- **问题**：
  - 第 27 条"异常 → 回到出问题前的状态"会重做动作，而这时可能已经合并成功了，只是没收到回执。
  - 第 28 条"任何非终点状态都可以取消"，和"已经开始合并就不能取消"矛盾。
  - 另外，异常只覆盖了"处理中"这一个状态。
- **Claude 的意见**：【照改】
  - 把这两条补充规则写进转换表的"条件"列；
  - 从异常恢复时，先去 GitHub 核对真实情况，再决定回到哪个状态；
  - 异常覆盖所有会调用外部的状态。

### 12.【中】`comprehension` 检查会卡住 CI（agy）
