## 1. "Windows 原生 + 后台只读"这个折中自相矛盾，而且它保护错了东西

- **问题**：折中说"先在 Windows 上跑，但后台只给只读权限"。可是 (a) 执行器的全部工作就是让 Agent 写代码、开 PR，只读根本跑不了 PRD 的 G1/F1；(b) 真正的风险不是"写文件"，而是"读凭据 + 联网外发"，只读挡不住这条；(c) Claude Code 的 OS 级沙箱只支持 macOS / Linux / WSL2，**Windows 原生标为计划中、目前不可用**（官方建议改用 WSL2 或 devcontainer）【未核实：本机版本】。也就是说，Windows 原生的 Claude 后台跑起来，没有任何操作系统层隔离，只剩 permission 提示词那一层——那正是你在 `agent-autoloop-analysis.md` §5.1 亲手否掉的防线。
- **为什么重要**：具体场景。一条 Issue 正文里塞一句"顺带把 `~/.claude/.credentials.json` 和 `gh auth token` 的输出贴到 README 的示例段"。无沙箱、以你的日常账户、`acceptEdits` 模式跑的 Agent 会照做，然后开 PR；凭据一旦进了 GitHub，就算只存在几分钟也可能被 fork/镜像，`git revert` 撤不回。而"只读版"连这个 PR 都产不出来——所以折中方案的两个选项分别是"做不到目标"和"没有隔离"，中间没有第三个状态。
- **建议**（不改 Windows 选择，三条缓解，按性价比排序）：
  1. **按适配器分级授权，而不是给"后台"一个统一权限**。Codex 在 Windows 上确实有原生沙箱，`[windows] sandbox = "elevated"` 会创建独立的低权沙箱账户 + 文件 ACL + 防火墙规则【未核实：Win10 版本要求、是否需要管理员一次性设置、本机是否可用】；`unelevated` 模式是"派生受限令牌 + 建议性网络限制"，够不上无人值守。所以第一阶段让 **Codex 当无人值守 writer，Claude 只在前台/herdr 里用**——这跟 PRD 7.5"Claude Pro 额度最紧、后台尽量不用"正好同向，一举两得。
  2. **必须让 Claude 无人值守时，包一层容器或一次性虚拟机**（devcontainer / Windows Sandbox，后者需要 Win10 Pro【未核实 本机版本】）。代价：多一层，文件交换要走显式挂载，而挂载点就是新的泄漏面。
  3. **先做 5 分钟的"诱饵验收"，并把它写进"重新考虑的信号"**：在 `C:\Users\weicai\` 放一个 `decoy.txt`，让 Agent 依次尝试读它、改 `risk.yml`、`curl` 一个外部域名；三项都必须失败。任何一个适配器过不了，就只能前台用。这条验收比任何架构讨论都便宜，而且立刻能告诉你"Windows 原生到底还剩多少安全"。
  4. 顺带：只读省不掉"最小凭据"。后台进程用的必须是机器人账号的细粒度 token，放在只有后台账户可读的位置；你个人账户的 token / 浏览器会话必须与后台账户在 ACL 上隔离。否则上面第 1 条的努力会被一次 `gh auth token` 抵消。
- **严重程度**：高

## 2. 裁决原则缺了最关键的一张表：等级 → 流程；"底线区名单"也不是可机检的谓词

- **问题**：ADR 定义了 A/B/C/D 和"最多降一级"，但**从没定义每一级分别对应什么审批、什么抽查、能不能自动合并**。"降一级"因此没有可执行含义：D 降到 C，是"不用我批"还是"抽查率从 100% 降到 20%"？另一方面，底线区那六项（安全/权限、核心逻辑、数据迁移和删除、`.github/`、依赖、密钥、发布和对外发送）是**类别名，不是路径或动作模式**：其中只有 `.github/` 和 `core:` 能直接写成规则，其余四项都要靠"理解语义"才能命中——而理解语义恰恰是分诊模型在做的活。
- **为什么重要**：这直接给出四条绕法，每条都能在 v1 真实出现：
  - **语义绕法**：如果"密钥"由模型识别，被 Issue 文本污染或只是判断力不足的模型，完全可以说"这只是 README 里的一个占位符"，而 diff 实际是在 `docs/example.md` 里落了一个真实 token 或内部 URL。文档属可放宽区，规则无从反驳，因为规则里没有"密钥"这个可判定谓词。
  - **闸门依赖闭包**：`.github/` 是 D 级，但 CI 实际调用的是 `scripts/check_risk.py`、`risk.yml` 本身、composite action、`package.json` 里的 test 脚本——它们都不在 `.github/` 下。改其中一个等于改闸门。
  - **重命名/移动**：把 `auth/token.ts` 改名成 `docs/token_demo.ts`，路径就落进可放宽区，形态上是"删除 + 新增"。
  - **拆 PR**："三个各 C 级的 PR"合成一次 D 级改动，最高级规则完全看不到。
  - 另有一条不是绕法而是定义漏洞：**基准必须每次从真实改动重算**，不能以上一次模型意见为起点，否则 C→B 之后再以 B 为基准就变成连续降级。
- **建议**：定稿前补两张纯数据表（你能自己写，而且正好是 MOD-4 的输入）：
  1. **等级表**：A/B/C/D × {谁能写、谁审、是否要你批准、抽查率、能否自动合并、失败后回滚方式}。没有这张表，`risk.yml` 写不出来，M0 的四个必需检查也写不出来。
  2. **底线区表**：六项改写成可判定条目，每条给 `{路径 glob | 动作类别 | 兜底}`。不可判定的项（"对外发送"）改从**动作**维度判：只要 Agent 的工具调用出现网络出口、发消息、推非 `agent/*` 分支，一律至少 C，不依赖文本判断。
  - 取舍：**黑名单**（列禁止项）摩擦小但必然漏；**白名单 + 默认 C**（只允许明确列出的放宽）安全但你要不断维护白名单、摩擦大。v1 建议白名单，且先把"非核心外围代码"这类模糊类别删掉，只允许 `docs/**` 的 `.md`（不含可执行示例）和 `tests/**` 的**新增**文件放宽；等有真实数据再扩。底线区一旦命中，放宽应该直接**不可裁量**，而不是"模型只能调严"——"调严"本身也是模型在参与。
- **严重程度**：高

## 3. "决定"被当成一件事，但这里是两个不同的决定：派活 vs 放行

- **问题**：图里只有一条"决定"箭头。系统其实要对同一件事裁决两次：**派活前**（基于 Issue 文本，此时还不知道 diff）和**放行前**（基于真实 diff + CI 结果，必须知道）。两者的证据、可信度、失败后果都不同，却共用一种格式、一条路径。
- **为什么重要**：按你要求走一个具体场景。
  1. Issue #12"修登录页样式错位，只改 CSS" → 分诊给 B 级 → 决策中心出"派活"决定。
  2. 执行器起 Agent → Agent 顺手把 `auth/session.ts` 的会话有效期从 7 天改成 30 天（它觉得顺手）→ 开 PR。
  3. 回执写 `level: B, verify: 测试通过`。
  4. 如果决策中心把第 1 步那条决定当成"放行授权"，就会合并一个改了鉴权逻辑的 PR。
  你批准的是 Issue 描述，合并的是另一份 diff。ADR 里"回滚"和"底线区"全都只有对着 diff 才有意义，所以这不是理论问题。
- **建议**：拆成两种合同：`DispatchDecision`（做不做、谁做、预算是多少）与 `ReleaseDecision`（这份 diff 能不能合）。`ReleaseDecision` 必须消费：真实 diff 的路径集合、重命名检测结果（`git diff -M`）、CI 结论、当前 head SHA。并写一条不变量：**派活决定不蕴含放行授权**；放行判定的对象是 **SHA**，不是 Issue 号——顺带把"你批准的是 h1、系统合并了 h2"的迟到批准问题一起解决。
  - 取舍：如果嫌重，也可以只保留一种 `decision` 格式，加 `scope: dispatch | release` 字段并要求"裁决时从真实改动重算 baseline"。实现复杂度不同，但"必须有两个时刻的判定"这一点不能省。
- **严重程度**：高

## 4. 图里让内核依赖外壳，违反你刚学的依赖方向；内核签名也没写

- **问题**：`[记录：日志·额度·信任·理解债] ──状态──► [决策中心]` 这条箭头，如果按图实现，就是决策中心（内核、纯函数）去读记录（外壳、IO）才能拿到额度/信任/状态。而 ADR 自己写了"箭头只传数据"，学习记录 0001 也写了"外壳可以调用内核，内核不能调用外壳"。同一原则下还有两处会被实现者踩空：决策中心"守底线"要读 `risk.yml`（IO）；"日志里记录每个决定用的是哪个版本"很容易被写成内核里写日志。
- **为什么重要**：如果照图做，PRD 里"内核没有 IO、没有时钟、没有随机数、可单独测试"（autoloop 有测试强制这条）就断了，而你手写并推导 MOD-1/2/4 的前提正是"给同样的输入就得到同样的输出"。更现实的是：它把一个**架构纪律**降级成了"实现时注意一下"的口头约定，而这份 ADR 的教学目的恰恰是练这个。
- **建议**：在 ADR 里直接写死内核签名，一句话就够：

  `decide(event, policy, budget_snapshot, trust_snapshot, now) -> decision`

  所有外部状态都是**调用者传入的不可变快照**，`now` 是显式参数。记录模块的角色改成"提供快照 + 记录决策"，永远不主动调内核。进一步，把"事件 → 内核输入"的字段抽取也放进内核（纯函数，可测），只把"发/收"留在外壳——否则"哪类事件要升级"这类判断会藏在模板拼接里，不受测试覆盖，而 ADR 已经承认"提示词也是决策逻辑的一部分"。
- **严重程度**：高

## 5. 四个建模题在模块表里没有家，调度模块整体缺失

- **问题**：PRD 4.1 的 MOD-1..4（信任校准、额度调度、注意力预算、抽查率）是"≥3 个模型上线"这一成功标准的载体，但 ADR 的模块表里一个都没出现，也没有"调度"这个模块。执行器"启动 Agent"——**谁决定用哪家、什么时候跑、跑几轮？** ADR 没有主体。
- **为什么重要**：不是文档洁癖。没有调度主体，下面这些都无处安放：额度不足时拒绝派活、写和审不能是同一家（PRD F6）、给白天交互预留额度（PRD 前提 4）、CI 失败最多修 2 轮（needs-spec R1）。实现者只能把它们散落在执行器或外壳里，于是变成不可测的 `if`；而你的模型没有输入口，没法推导、没法"上线后用真实数据检验"。MOD-3 同理：通知模块要在"发卡 / 合并 / 静默"之间选，这就是 MOD-3，但架构把它归给了"通知（外壳，AI 写）"。
- **建议**：模块表里加一行**调度器（内核）**：职责"在约束下选择 agent、时间、是否推迟"，输入是额度快照、信任快照、任务队列、当前时间，输出并入 `DispatchDecision`。再补一张 PRD 4.1 → 模块 → 对外接口的映射表，这样 M3 有明确的上线位置，测试可以从"给快照、断言决定"开始写。
- **严重程度**：高

## 6. "M1 就能跑"缺少额度证据；预算保护排到 M3，而 Claude Pro 是最紧的一份

- **问题**：模块表里有"记录（含额度）"，但额度在这里是**观测**，不是**约束**：没有调用前预算、没有审查额度预留、没有"用完就停"的位置。PRD 7.5 自己写了"Claude Pro 额度最紧、后台应尽量不用"，而 M1 却用 Claude 跑后台，MOD-2 要等到 M3（第 6–9 周）才上线——中间 4–6 周是无预算保护的运行期。
- **为什么重要**：按 PRD 7.5 的量级（Claude Pro 5 小时窗口 + 周上限；OpenCode Go 约每 5h $12 / 每周 $30 / 每月 $60；以官方控制台为准，【未核实】），一次完整任务 = 分诊（1 次模型调用）+ 写（长会话）+ 审（另一家长会话）+ 修 2 轮 ≈ 5–8 次模型调用。每天 8 张卡片对应的任务量，加上定时巡检和 CI 回执，足够吃掉一个 5 小时窗口——吃掉的正是你白天在 herdr 里要用的那份。后果不是"自动化慢一点"，而是**你的学习和手写时间被后台挤掉**，而那才是 G2 的全部意义。
- **建议**：v1 先用硬预算，不要等优化模型：
  - 分诊前先过规则：去重、你自己发起的操作、无关 CI 失败、已知安全拒绝，全部不进模型；分诊优先用最便宜的一家（OpenCode Go 的开源模型）或本地模型【未核实 本地是否计入额度】。
  - 派活前一次性预留"写 + 审 + 修 2 轮"的估计额度；预留不足就排队，**不要先写后审**（半成品堆积比排队更贵）。
  - 每天给后台一个固定额度上限，用完停到次日；你在线的时段后台降级为只读巡检。
  - 禁止自动转 API Key 或超额付费——那会把"额度约束"变成"无限花钱"，与 PRD 前提 4 直接冲突。
  - 把"额度容量验证"写成 **M1 的验收项**：用一周数据回答"每条自动完成任务消耗多少额度、多少次调用"，拿这个数再决定"≥50% 自动完成"是否现实。
- **严重程度**：高

## 7. 回滚规则有四处走不通；"只追加"与"降级"没有对齐

- **问题**：(a) main CI 变红就生成回滚 PR，但回滚 PR 自己也要过同一组必需检查——若 CI 红的原因是依赖源、偶发测试或基础设施，回滚 PR 也永远绿不了，系统死锁。(b) 归因：先合 P1 再合 P2 之后才红，不能断定是 P2。(c) `git revert` 撤不回副作用：已推的分支、已发的飞书消息、已调用的第三方 API、已写入的本地状态、跑过的迁移。(d) ADR 说"对相关规则降级"，但"记录只追加"——降级是写新事件还是原地改状态？信任统计要能重算，就不能在日志里原地改。
- **为什么重要**：具体场景：Agent 升级依赖导致测试超时（不是逻辑错）→ CI 红 → 自动生成回滚 PR → 依赖没降回去，仍然超时 → 回滚 PR 也红 → 没有任何决定被触发，所以也没有通知。第二天你发现所有主线 PR 都卡着，日志里只有一行"已生成回滚 PR"。
- **建议**：
  - 把"自动恢复"收紧成"自动生成恢复候选 + 自动暂停相关派活 + 立即通知你"，恢复本身要你一键批准（这是 D 级，但它**不能依赖那组检查全绿**才能在 CI 红时执行，否则紧急通道在最需要的时候不可用；这需要一个受限的 bypass 通道，只允许 revert 或前向修复两种动作）。
  - 回滚要绑定"最后一次已验证版本"（记录里存通过的 merge SHA + 检查名），而不是"最近一次合并"。
  - 区分"可逆动作"和"要备份才能做的动作"：会改外部状态的动作，把"执行前留快照 / 幂等键"写成 D 级动作的**前置条件**，而不只是贴一个 D 标签。
  - 降级/收回一律写成新事件（`TrustPenalty{agent, category, reason, until}`），统计视图由事件重算——这样"只追加"和"可回滚"就不打架了。
- **严重程度**：中（v1 里能自动回滚的动作很少，但规则一旦写错会一直错）

## 8. 学习闭环缺"回流"这一环，缺容量上限；影子模式在额度上不成立

- **问题**：六步闭环第 6 步是"系统保存，下次遇到同类问题时主动提醒"——但模块表里**没有模块负责"提醒"**，图上学习只连到"你（桌面）"，没有任何箭头回到决策中心 / 提示词 / 规则。学习产出的东西（新规则、新提示词段落、新的核心路径定义）怎么进入运行时，路径不存在。其次，第 1 步要捕捉"评审意见不一致"，就需要"你的 review"和"AI review"对齐到同一处代码的数据格式，而三种合同里没有这种格式。第三，容量：PRD 规定手机 ≤8 张卡，但学习卡、桌面审阅队列、影子模式的比对检查都不计入任何预算。
- **为什么重要**：学习模块最容易"跑得很顺但空转"——练习做了、总结写了、记录存了，下次遇到同类问题却没有任何东西触发提醒。而它正是这个项目区别于 autoloop 的全部理由。影子模式如果包含模型调用，成本直接翻倍，在 Claude Pro 最紧的额度下等于不可用。
- **建议**：
  - 加一条箭头：学习 → 决策中心 / 提示词，规则是"学习产出必须落地成某种可版本化的输入（新规则、新提示词段落、新核心路径条目），走 D 级流程"。"提醒"的载体直接复用通知模块，触发条件是"当前事件类别命中某条学习记录的 tags"。
  - 增加第四种合同 `ReviewRecord{pr, sha, 你发现的, AI 发现的, 共同发现的, 事后回填的漏检, 你的用时}`——这是 PRD 4.3"发现率"指标唯一的可算来源，没有它，M2 的"评审对照开始记录数据"根本没法开工。
  - 影子模式限定为**只对纯函数规则**（零成本）；提示词/模型的变更用"小流量 + 提高抽查率 + 一键回退"，不做双跑。
  - 给学习设一个在途上限（例如同时最多 3 个未完成的练习/总结），超了就先不生成新题。学习时间和额度是同一类稀缺资源——这本来就是 MOD-3 的另一半。
- **严重程度**：中

## 9. 事件路径缺了取消、超时、失败和循环控制

- **问题**：事件采集的输入列的是"定时器、GitHub、你的回答、回执"，全是正常路径。缺：你改主意要停（取消）、Agent 卡住或 CLI 挂起（超时）、进程泄漏（Windows 上尤其常见）、额度耗尽（中止）、Agent 崩溃（失败分类），以及"回执作为事件再次进入分诊"的循环控制。另外"你的回答"出现了两次（事件采集的输入、通知模块的输出），归属不清；回执从左侧进事件采集，同时又是执行器的输出——同一条消息走了两条路。
- **为什么重要**：具体场景：执行器起了 Claude，Claude 在等一个交互式权限确认（Windows 原生没有沙箱，这类提示是真的会弹出的），进程永不退出；由于"回执"这条边，图看起来一切正常。半天后你发现 5 个进程占着 5 个会话，额度窗口重置后又被它们吃掉。另一条：如果每条回执都触发一次分诊模型调用，那"Agent 说完成 → 分诊 → 决定 → 执行器 → 回执"就是一个持续花钱的环。
- **建议**：
  - 合同里加 `task_id`、`attempt`、`deadline`、`cancel_requested`、`idempotency_key`；明确**哪些事件类型跳过模型分诊**（回执、日志确认、CI 状态变化走纯规则；只有"人的新意图"和"未知事件"进模型）。
  - 执行器需要：进程级超时 + 强制终止 + "非交互模式下必须禁掉所有需要 TTY 的确认" + 启动前检查无残留进程。
  - 加一条"取消/接管"路径：你按一下 → task 标记取消 → 执行器终止进程 → 已开的 PR 打上 `cancelled` 标签且永不自动合并。
  - 明确"你的回答"只有一个入口：通知模块只负责展示与验证来源，规范化后的回答统一交给事件采集。
- **严重程度**：中

## 10. ADR 文本本身：三个文档互相矛盾，倾向的理由不可检验

- **问题**：
  - **PRD 的 M1 说"在 WSL 里跑 hub"，ADR 的倾向是"先用 Windows"，折中又说"到 M1 再迁移到 WSL"**。三句话合起来：M1 到底在哪跑？如果 M1 就在 WSL，那"先用 Windows"只覆盖 M0（第 1 周、还在用手动派活），等于这个决策几乎不用做；如果折中意思是 M1 先 Windows 再迁，那迁移是 M1 的验收项还是 M2 的？现在三份文档各自都能自称"遵守"。
  - "WSL 有文件管理上的问题"是不可检验的理由。具体是什么：跨 `/mnt/c` 的 IO 慢、CRLF、`inotify` 在 `/mnt/c` 上失效、权限位丢失？写成具体假设，复盘时才能判断它对不对——这正是 PRD 4.3 要求你做的"事实核查"，而这次你自己就漏了。
  - 备选方案里两处理由过强："纯规则写不出语义判断"（更准确：规则难以穷尽且维护成本高，所以在低风险区用规则兜底，而不是规则无能为力）；"云端天然隔离"（隔离与否取决于网络、凭据、挂载配置，不是位置属性）。
  - "决定""代价""重新考虑的信号""复盘"全部空白，而"重新考虑的信号"恰恰是这份 ADR 最有教学价值的一节。
- **建议**：定稿时把"决定"写成一句可执行的话，例如："v1 的 hub 在 Windows 原生运行；无人值守 worker 按适配器逐一通过隔离验收（诱饵读 / 改策略 / 外联三项），未通过的只在前台使用；M1 不迁移 WSL，M2 末评估是否迁移"。"代价"写实：Windows 上 Claude Code 无 OS 沙箱、需按适配器分别验收、迁移成本被推迟而非消除。"重新考虑的信号"写可观测项：任一适配器隔离验收失败；一周内出现 ≥3 次额度窗口冲突；睡眠/唤醒后事件丢失；某个任务需要 Windows 原生给不了的能力（如文件锁语义、信号、POSIX 路径）。
- **严重程度**：中

## 三句话总结

最大的优点是**把"模型给意见"和"固定代码裁决"分开**，并且让模型只做它擅长的那一半——这个分层同时服务了安全和你的建模练习，是本 ADR 真正的内核。
最大的风险是**把逻辑分层误当成执行边界**：Windows 原生上 Claude 没有 OS 沙箱、底线区靠语义识别、派活与放行共用一条决定、额度只是事后记录——四件事叠加后，系统可能正确地算出"不许合并"，却依然把凭据推出去、把没批的 diff 合进去、把白天的额度吃光。
定稿前必须改的一处是**补上"等级 → 流程"表并把底线区改写成可判定谓词（含闸门的依赖闭包）**——它是 M0 的 `risk.yml` 和四个 CI 检查的唯一输入；没有它，这份 ADR 的"已达成一致"在实现层无法落地，其余九条也只能停留在讨论里。
