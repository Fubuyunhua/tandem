# 红队修复审核（Claude，范围 4472229、27eebd8、cd8338f）

结论：**方向对，有 1 条需要改的问题（R1），2 条小问题。**

## R1（需要改）CI 在"待验收以外"变红时，任务会卡住
`_on_ci_red` 在任务已经离开"待验收"后收到同一提交的红灯，现在的做法是：留在原状态，清掉绿灯、审核、批准和指定审核者。

问题出在后面：清掉证据之后，没有任何事件能让任务继续往前走。
- **待AI审核**：`designated_reviewers` 被清空，之后到达的审核结论没有指定审核者可以对上，也不会重新派审核。任务卡死。
- **待你审核**：`approved_sha` 被清空。你再批准时，合并守卫（transition.py 第 185 行）会因为 `ci_green=False` 拒绝合并，你只能驳回或取消。不算卡死，但界面上看不出"为什么批准不了"。
- **待合并（MERGE 还没发出）**：合并动作的前提已经不成立，但状态还是"待合并"。

建议：
- 合并还没发出时（待AI审核、待你审核、待合并且 MERGE 未发出），按 #10/#11 处理：退回"待处理"，记一次验收失败，达到上限就进入"待你介入"。代码在这个提交上是坏的，就应该返工。
- MERGE 已经发出时，保持现在的做法：留在原状态，只撤证据，由 #26 核对合并结果。注释里已经写了这一点。
- 补测试：上面每个状态各一条，断言事件发生后的状态，以及之后还有路可走。

## R2（小）删除文档不再算可放宽的改动
`all_paths_relaxable` 要求 `after_mode == "100644"`，删除时 `after_mode` 是 `000000`，所以"只删一个文档"从 A 变成了 B。偏保守，可以接受，但这是行为变化，请在提交说明或 README 里写一句。

## R3（小）OID 校验放在 `_dispatch` 入口，会和 pi 的 40c3f77 重叠
pi 在 feat/m1-runnable 上新加了"方案事件必须带 SHA"（40c3f77）。合并时两边的检查会在 `_dispatch` 和 `_on_plan_*` 里各出现一次。请合并时只保留一处（入口处的 OID 格式校验 + 处理函数里的"与方案 SHA 一致"校验），并统一拒绝原因的文案。

## 已确认没问题
- `resolve_oid` 使用 `--verify --end-of-options <ref>^{commit}`，可以挡住以 `-` 开头的参数注入和非 commit 对象。
- diff 在临时 bare 仓库里只借用对象库，并加了 `--no-ext-diff --no-textconv --ignore-submodules=none`。用户自己的 diff 驱动、textconv 和 ignoreSubmodules 都绕不过去。
- `**/migrations/**` 现在也能匹配仓库根目录的 `migrations/`；大小写统一用 casefold。
- 符号链接指向受保护路径或仓库外的路径时，会进入底线原因。
