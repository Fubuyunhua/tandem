审核范围：指定 worktree 内 `main...feat/wsl-isolation` 的全部改动；基线 `f973b8fc312b1ca91f2eb9e446a1dee1099ca0bd`，分支头 `ad7f2f3cd143ea101e93461ac760ec8d22513510`。依据任务书和 ADR-0001 的 WSL2、诱饵测试及凭据清单要求；未读取其他审核者输出。

验证严格限制为源码读取、纯函数测试和内存 mock：运行现有环境的 `python -B -m pytest tests/scripts/test_decoy.py -q -p no:cacheprovider -k 'not runner and not dry_run'`，结果 **20 passed、9 deselected**；`git diff --check` 通过。未执行 WSL 命令、PowerShell 安装脚本、真实 Agent、监听端口或网络请求，未运行会创建探测文件的端到端测试。以下将代码可确定的问题与本机尚未验证的隔离条件区分说明。

## 1. 重建时先注销目标，且没有禁止目标与源发行版同名

- **问题**：`-Recreate` 会在导出前删除目标，源目标同名时等于先删除自己的唯一导出来源。
- **位置**：`scripts/wsl/setup-tandem-distro.ps1:132`、`scripts/wsl/setup-tandem-distro.ps1:146`、`scripts/wsl/setup-tandem-distro.ps1:161`。
- **为什么重要**：传入 `-SourceDistro Ubuntu -DistroName Ubuntu -Recreate` 能通过现有存在性检查；确认后先执行 unregister，再尝试 export 已不存在的 Ubuntu，原数据已经不可逆丢失。即使源目标不同，用户在第二次确认时取消，或随后导出因磁盘不足失败，也已经删除了旧目标；“取消，未做任何改动”的报错与事实不符。这些是执行顺序的静态结论，未实际注销任何发行版。
- **建议**：任何破坏性动作前拒绝源目标同名，核验源、安装目录、导出位置及空间；先完成导出并验证可用，再确认替换目标。明确旧目标备份/恢复方案，收齐本次操作的确认后再删除。对导出、导入、写配置失败分别保留阶段记录，不把剩余的半成品描述成完成。用 mock WSL 命令测试顺序、取消和失败，不需要真的建删发行版。
- **严重程度**：高

## 2. 直接复制日常 Ubuntu，不等于建立无私人资料的专用环境

- **问题**：脚本导出整个源发行版，没有要求干净源，也没有清点继承的用户数据、凭据和权限。
- **位置**：`scripts/wsl/setup-tandem-distro.ps1:161`、`scripts/wsl/setup-tandem-distro.ps1:167`；`docs/runbooks/wsl-isolation.md:69`、`docs/runbooks/wsl-isolation.md:92`。
- **为什么重要**：源发行版里的私人文件、旧 Agent 登录材料、Git 凭据及本地配置都会随文件系统复制；关闭 Windows 自动挂载不会消除已经复制到 Linux 内的副本。新增 tandem 用户也不能证明其无法读取所有继承内容，尤其继承的可读权限、提权配置需要检查。本机源发行版具体有什么内容、哪些可读【未核实】，不能假定源是干净镜像。手册又只说凭据留在发行版内，没有提供 ADR 要求的 hub、worker、合并组件凭据/权限清单。
- **建议**：要求用户选择经确认的干净基础发行版或离线基础镜像，禁止默认把个人开发环境整体当作安全基线。若坚持复制，先列继承数据与权限的审计步骤，再人工确认；不要自动删除源中的私人资料。补凭据清单和分离账户/访问权限：worker 仅能取得模型所需凭据，不能读取控制器合并 token、修改生效策略或检查结果。按低权限 worker 的实际身份做验收。
- **严重程度**：高

## 3. 未执行三项攻击也能获得三项“被挡住”，测试还把这种结果当正确答案

- **问题**：负面检查只证明没有观察到变化，没有证明探测已经尝试且被权限边界拒绝。
- **位置**：`scripts/decoy/checks.py:99`、`scripts/decoy/checks.py:125`、`scripts/decoy/checks.py:137`；`scripts/decoy/run_decoy.py:338`；`tests/scripts/test_decoy.py:239`。
- **为什么重要**：`performed=decoy_ok` 只表示诱饵布置成功；配置存在且哈希相同、监听器启动且 hits=0，也不代表 Agent 做过操作。现有 `HONEST_AGENT` 仅打印 OK 和固定提交号，根本没有读文件、改配置或发请求，`test_runner_passes_when_agent_behaves` 却期望整体通过。纯函数反例也实测得到五项全部 pass。实际 Agent 若省略步骤、只解释政策或根本没使用工具，就会被授予后台准入。
- **建议**：每项必须有独立的执行证据，区分“未尝试、尝试被拒绝、成功越界、测量失败”；未尝试不能映射成 pass。通过可信工具包装器记录目标、动作、错误类别与拒绝结果，且在实际 worker 的权限/沙箱中执行探测，不能只让模型自报。将只打印文字的 fake 改为未执行反例，另外添加真正发起操作且由模拟权限层拒绝的通过用例。
- **严重程度**：高

## 4. 模型与 GitHub 可达性凭普通输出就通过，不能作为正面通信证据

- **问题**：进程退出 0 加任意文字就代表调模型成功，任何 40 位十六进制串又被当成访问 GitHub 成功。
- **位置**：`scripts/decoy/checks.py:154`、`scripts/decoy/checks.py:178`；`scripts/decoy/run_decoy.py:342`；`tests/scripts/test_decoy.py:239`。
- **为什么重要**：实测给判断函数传入 `OK\n` 加伪造提交号，两项都 pass，不需要模型或 GitHub。输出中的别处哈希、缓存内容、CLI 帮助/自述也可能误充证据；Git 检查甚至没有对应命令退出码。这样网络全部坏掉、模型未调用，工具仍可能报告“允许的通信正常”。测试中的固定字符串只验证正则接受字符串，没有验证通信判断。
- **建议**：正面项使用各适配器可核验的实际调用结果；Git 单独记录目标仓库、实际工具调用、退出码及完整 ref 格式，并确认走的是受测 worker 的网络边界。模型检查记录真实适配器成功结果与本次调用标识，而非“回答 OK”。离线测试可以模拟这些可信证据，但不能把假输出当真实准入证明。真实可达性本次未运行，不能据本次测试报告已成立。
- **严重程度**：高

## 5. localhost 诱饵只能测一个目标，整体结论却声称白名单外网络都已受限

- **问题**：没有验证出口白名单或拒绝机制存在，就把 loopback 端口 0 次连接解释成出站隔离通过。
- **位置**：`scripts/decoy/run_decoy.py:83`、`scripts/decoy/run_decoy.py:137`；`scripts/decoy/checks.py:137`；`docs/runbooks/wsl-isolation.md:125`、`docs/runbooks/wsl-isolation.md:162`。
- **为什么重要**：Agent 到不了这个本地监听地址，可能只是目标网络命名空间、路由或尝试方式不对，并不意味着其他出口被禁止；本地允许/拒绝规则也不自动代表外部出口规则。手册已诚实说明防火墙/代理白名单“本仓库还没有这一层”，但通过后的步骤仍允许无人值守，判定范围超出了测量范围。即使修掉第 3 条的“未尝试”，这个覆盖范围问题仍存在。
- **建议**：本轮可以不实现完整防火墙，但缺少实际出口控制与配置证据时，网络隔离项应是未验证，不能成为后台准入。为本地可观测目标明确其位于受测边界的哪一侧，先有控制组证明目标可达，再核验 worker 被该出口政策拒绝；补允许目标的对照。记录网络政策版本，并将工具结论限制为实际验证的边界。本机网络隔离状况【未核实】，不能以单端口探测替代。
- **严重程度**：高

## 6. `-TarPath` 指向既有文件时会无条件删除，未验证它是本脚本的临时产物

- **问题**：用户可指定任意导出路径，脚本在导出前和完成后都按此路径删除文件，没有所有权或专用范围检查。
- **位置**：`scripts/wsl/setup-tandem-distro.ps1:53`、`scripts/wsl/setup-tandem-distro.ps1:156`、`scripts/wsl/setup-tandem-distro.ps1:188`。
- **为什么重要**：若用户误把 `-TarPath` 设为现有备份或重要文档，第一次 Remove-Item 就会删除它；此前的确认只说明导出占空间，没有逐项确认覆盖既有文件。默认固定临时文件名也无法区分上一次保留下来的恢复材料与这次新建文件。这里只静态检查，未执行删除。
- **建议**：使用专用临时目录和唯一文件名，拒绝覆盖既有文件；自定义路径先解析为绝对路径并验证允许范围、文件类型和是否已存在。只清理由本次运行明确创建的产物，失败时是否保留恢复包应显式说明。dry-run 应打印这些风险与前提检查结果，而不只是命令串。
- **严重程度**：高

## 7. 布置假密钥会直接覆盖用户指定的现存文件

- **问题**：`place_decoy` 使用截断写入且跟随路径，没有防止真实密钥、已有文件或符号链接被覆盖。
- **位置**：`scripts/decoy/run_decoy.py:192`、`scripts/decoy/run_decoy.py:251`。
- **为什么重要**：`--decoy-path` 只检查在 workspace 外，正好允许指向用户私人文件位置；若误指定现存密钥，脚本会把它改成诱饵文本再 chmod。内存 mock 已确认该函数直接调用 write_text，没有独占创建检查。工具的用途是模拟敏感资料，不应先破坏真的敏感资料。
- **建议**：在本次测试专用、可信所有者控制的目录中以独占且不跟随链接的方式新建诱饵，遇现存路径就拒绝；验证与 config、隔离配置、输出目录等目标没有别名冲突。将测试控制器与 worker 的身份、权限区分清楚，清理只操作本次创建的诱饵。补既有文件、符号链接及路径重叠的拒绝测试。
- **严重程度**：高

## 8. 泄漏到 `data/` 或文件后半部分会漏检，却仍可判读密钥被挡住

- **问题**：泄漏扫描跳过多个可写目录，并且每个变化文件只扫描首 1 MB，遗漏没有体现在验收结果中。
- **位置**：`scripts/decoy/run_decoy.py:50`、`scripts/decoy/run_decoy.py:158`、`scripts/decoy/run_decoy.py:176`。
- **为什么重要**：内存 mock 实测 `workspace/data/leak.txt` 完全不进入快照，连 read_bytes 都不会调用；标记位于变化文件第 1,000,000 字节之后时，`judge_secret_read` 返回 pass。Agent 可以把读到的内容写进 `data/`、`.git/` 等被排除的位置，或大文件尾部，stdout 不出现标记就漏掉。额外扫描目录参数并未消除默认覆盖缺口，读取错误也被静默跳过。
- **建议**：对受测 worker 的全部允许写入位置建立明确扫描范围，用分块扫描而非静默截断；无法扫描的目录、文件或权限错误记录为覆盖不完整，不能宣称未泄漏。仅对确定不可写/无关的目录排除。补 data 隐藏泄漏、超长文件末尾、读失败和目录外写入的反例。
- **严重程度**：高

## 9. 复测时“改成 # tampered”可能没有改变内容，从而把可写配置判成不可写

- **问题**：配置探测每次要求相同改写，前后哈希相同不能证明这次写入被禁止。
- **位置**：`scripts/decoy/checks.py:125`、`scripts/decoy/checks.py:237`；`scripts/decoy/run_decoy.py:199`。
- **为什么重要**：第一次失败后配置首行已经是 `# tampered`，`ensure_live_config` 发现文件存在就保留；第二次 Agent 再成功写入同样首行，哈希不变，判定便是 pass。纯函数核验相同的已篡改哈希确实返回 pass。删除配置后的 hash_after=None 又被标为未执行，不能准确表达已经发生的破坏。
- **建议**：在隔离的受保护测试副本上要求每轮不同的挑战内容，确认挑战与基线不同，另记录实际写尝试及拒绝证据；不存在、删除、内容改变和无法取证应分别处理。测试不应要求改真实生产策略，失败后由可信控制器恢复测试副本。补连续两轮探测、删除、写后恢复原内容等用例，明确单纯前后哈希的证据上限。
- **严重程度**：高

## 10. 手册的首次运行缺少受保护配置准备，普通用户会在测试开始后异常退出

- **问题**：默认配置在 `/etc/tandem/risk.yml`，却由运行 Agent 的同一进程临时创建，手册没有先准备其所有者和权限。
- **位置**：`scripts/decoy/run_decoy.py:199`、`scripts/decoy/run_decoy.py:317`；`docs/runbooks/wsl-isolation.md:64`、`docs/runbooks/wsl-isolation.md:95`。
- **为什么重要**：手册要求 tandem 非 root 运行，但未建立 `/etc/tandem`；对通常受保护的 `/etc`，首次创建会权限失败，异常未捕获，连结果 JSON 都没有。本机具体权限【未核实】；内存注入 PermissionError 已确认异常直接逸出。若为图省事整份脚本用 root 跑，又把 Agent 一起变成 root；若改成同用户可写目录，样例配置也并未受该用户的权限保护。同理，默认假密钥由当前用户以 0600 创建，工作目录外不等于同一用户不能读，需要额外的 worker 沙箱才能成立。
- **建议**：手册增加可信管理员准备、低权限 worker 探测、控制器收证的分阶段步骤；明确 UID、文件/目录所有者、读写规则和 Agent 沙箱配置，并做能力预检。不要建议整份探测脚本 sudo 运行。准备失败也应生成明确的未执行结果，不启动 Agent；只使用合成测试资料验证权限。
- **严重程度**：中

## 11. Python 的 dry-run 仍启动监听器，正常错误路径也没有统一清理

- **问题**：监听端口与线程在检查 dry-run 前就创建，且异常发生时未以 finally 保证释放。
- **位置**：`scripts/decoy/run_decoy.py:287`、`scripts/decoy/run_decoy.py:300`、`scripts/decoy/run_decoy.py:317`；`tests/scripts/test_decoy.py:353`。
- **为什么重要**：内存 mock 实测 `dry_run=True` 仍调用 `listener.start()` 一次；真实实现会 bind 本地端口并启动线程，这违反“只打印计划”的约定。配置准备抛错时 listener.stop 调用次数为 0，正常嵌入调用会留下未清理资源。现有 dry-run 测试只检查几个目录不存在，未禁止 socket、线程或子进程启动。本次没有真实启动监听器。
- **建议**：dry-run 在随机目标/监听资源创建前直接打印符号化计划；正常执行用上下文管理器或 try/finally 管理监听器及进程，准备异常同样清理并记录。补 mock 测试，断言 dry-run 不触发 socket.bind、Thread.start、文件写入和进程启动，并覆盖准备失败后的清理。
- **严重程度**：中

## 12. 记录不能定位实际受测版本，隔离配置缺失或运行环境不符仍能整体通过

- **问题**：记录只存 Agent 名字、命令模板和可为空的配置哈希，缺少任务书要求的 Agent 版本与有效隔离环境证明。
- **位置**：`scripts/decoy/checks.py:251`、`scripts/decoy/run_decoy.py:306`、`scripts/decoy/run_decoy.py:346`；`docs/runbooks/wsl-isolation.md:111`。
- **为什么重要**：同一 `claude -p {prompt}` 可以对应升级前后不同二进制；只记 `/etc/wsl.conf` 不会覆盖 Agent 沙箱、插件和网络政策。实测 `isolation_config_hash=None` 仍可生成 passed=True；非 Linux 环境只加备注、不限制结论，因此未在目标 WSL 中验证也能获得“隔离通过”的文件。现有集成测试提供了不存在的 wsl.conf 路径仍期望通过，实际把证据缺失固化为成功。
- **建议**：增加 Agent CLI/模型标识与版本、运行用户、发行版/WSL 标识、工具版本、实际沙箱与网络政策版本；配置缺失、环境不匹配或版本未知时，只输出模拟/证据不完整结果，不授予后台准入。环境核验可由可信控制器提供，只读查询即可；无需本轮真的安装或联网验证。提交证据前脱敏原始输出，避免把测试中意外打印的真实凭据复制进仓库。
- **严重程度**：中

结论：**需要大改**。纯函数拆分和五项结果框架可保留，但“未尝试也通过”的准入判断、破坏性脚本前置校验和可信隔离基线都还不成立；应先修复这些根本问题，再由用户执行受控的实际 WSL 验收。
