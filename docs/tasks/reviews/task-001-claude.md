# task-001 审核意见 · Claude

审核对象：`feat/m1-runnable` 相对 `main` 的改动。我在本地跑过 ruff、pyright、pytest（164 个测试通过）和 `tandem demo`，都通过了。我在写这份意见之前没有看 Codex 的审核结果。

整体评价：内核和外壳的边界很清楚，`decide()` 基本完整实现了第七版的转换表，所有会产生外部副作用的动作默认都是 dry-run。问题主要集中在"数据从哪来"：有一处把 Agent 的自述当成了事实。

## 1.【高】等级是按 Agent 自己报的改动算的，不是按真实的 diff 算的
- **位置**：`src/tandem/shell/receipt.py:119-124`（从回执里解析 `changes`）；`src/tandem/shell/cli.py:258`（把 `receipt.changes` 直接放进 `CODE_SUBMITTED` 事件）
- **为什么重要**：ADR-0001 的两条核心规则都要求以真实改动为准：一条是"完成与否只看外部证据，回执只是自述"，另一条是"每次都根据真实改动重新算级别"。现在的写法下，一个 Agent 改了 `src/tandem/core/`，只要在回执里写 `"changes": {"paths": ["docs/a.md"]}`，任务就会被判成 C 级甚至 B 级，然后自动合并。整套等级制度就这样被绕过去了。
- **建议**：
  - 回执里不再接受 `changes` 字段。如果 Agent 填了，也忽略掉，并记一条警告。
  - 外壳新增一个"改动采集器"，根据提交编号自己算出 `ChangeSet`：用 `git diff --name-status -M <base>...<sha>` 取得改动的路径、删除的文件和改名的路径对，再统计断言数量的变化，并跑一遍密钥扫描。
  - 采集器要做成可替换的接口：测试和 demo 用假的实现，但它属于外壳，和 Agent 的回执没有关系。

## 2.【中】`risk.yml` 的运行模式和 M1 的决定矛盾
- **位置**：`risk.yml:6-8`
- **为什么重要**：注释写的是"M1 只有 Claude，所以用 single_agent"，但实际的值是 `multi_agent`。M1 真正跑起来以后，任务会去等一个并不存在的 AI 审核者，最后进入 R03"待你介入"，而不是 ADR 定好的"单 Agent 模式下所有等级都由你审"。
- **建议**：默认值改成 `single_agent`。`demo` 需要多 Agent 模式，就在 demo 代码里显式覆盖这个设置，不要靠默认配置。

## 3.【中】你的批准绑定的是命令执行那一刻的版本，不是你看到的那一版
- **位置**：`src/tandem/shell/cli.py:51`（`_event` 用的是执行命令时读到的 `task.state_version`）；`src/tandem/core/transition.py` 中的 `_on_your_approval`、`_on_intervention_approved`（都没有核对 `event.sha`）
- **为什么重要**：设想这样一个过程：你看完提交 X，准备批准；在你敲下 `tandem approve` 之前，任务被打回、重做，现在停在提交 Y 上等你审。这时命令读到的是最新的版本号，于是你对 X 的批准被用在了 Y 上。这正是评审第 2 条说的"你批准了旧版本，系统却合进了新版本"。
- **建议**：`approve` 命令要求带上 `--sha`，也就是你看到的那个提交编号。内核对"你批准"和"人工审核通过"这两类事件强制核对 `event.sha == task.latest_sha`，对不上就忽略这个事件。

## 4.【中】额度用完的标记只存在内存里，重启后就没了
- **位置**：`src/tandem/shell/runner.py:39-52`（`QuotaTracker`）
- **为什么重要**：程序一重启，"Claude 额度已用完"这个标记就丢了，系统会把任务再派给 Claude，然后马上又失败。电脑睡眠唤醒、程序重启，在 M1 都是常见的情况。
- **建议**：把额度状态存进 store。可以从事件日志里重放得到，也可以单独建一张表。

## 5.【低】Windows 下把输出重定向时，中文会变成乱码
- **位置**：`src/tandem/shell/cli.py` 的输出部分
- **为什么重要**：我在 Windows 上通过管道读取 `tandem demo` 的输出时，中文全是乱码。原因是重定向后 Python 用的是系统代码页 cp936。以后外壳要读取命令行的输出，也会遇到同样的问题。
- **建议**：在 CLI 入口调用 `sys.stdout.reconfigure(encoding="utf-8")`，`stderr` 也一样处理。

## 6.【低，待用户决定】验收失败次数在新提交后不清零
- **位置**：`src/tandem/core/transition.py:488`；pi 在回报里的第 9 条选择
- **说明**：任务书没有写这一点，是 pi 自己做的选择。理由是"否则 CI 红可以无限循环"，这个理由说得通。但它的副作用是：一个任务前期 CI 红过 2 次，后来经过审核、修改，又红了 1 次，就会直接进入 R01。这不算代码错误，而是一条规则需要你来定。

## 结论
**修改后可以交给用户审核。** 第 1 条必须改；第 2–4 条建议这一轮一起改；第 5 条顺手改掉就行；第 6 条交给用户决定。
