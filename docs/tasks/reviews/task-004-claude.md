总体：边界做得认真——`gh` 用参数列表调用、正文走标准输入、错误信息脱敏、合并前核对 head SHA + PR 状态 + CI、服务端用 `sha` 参数做原子条件、模拟执行不会推进到已合并、核对时校验已合并 PR 的 SHA。下面是要改的地方。

## 要改

### K1（高）D 级任务的 CI 永远是红的——和 task-003 的闸门冲突
- `GhGitHub.get_ci` 把提交上**所有**检查都算进来。task-003 的 `risk-level` 检查在 D 级时故意以退出码 3 失败。
- 结果：D 级任务一到"待验收"就收到 `CI_RED`，被打回修改，3 次后 R01 失败——D 级任务永远合并不了。用户的规则是"CI 绿才能合并、人不能越过 CI"，所以这不是能靠人工放行解决的。
- 这是 task-003 和 task-004 之间的**架构问题**，要用户拍板（见交接说明）。在那之前，适配器至少要：只看配置里列出的"必需检查"名字（例如 `risk.yml` 里 `required_checks: [check]`），而不是"提交上的全部检查"。

### K2（中）缺必需检查时会过早判绿
- 只要已出现的检查都成功就判 GREEN。工作流刚排队、某个检查还没登记时，可能只看到一部分。`skipped` 也算绿：一个被跳过的 `check` 会被当作通过。
- 改：按必需检查名单逐个核对，缺任何一个就是 PENDING；必需检查是 `skipped` 判 RED 或 PENDING，不能判绿。

### K3（中）一次 Issue 列表读取失败，把所有 GitHub 任务都打成异常
- `poll()` 里 `list_issues` 失败时，对所有未结束的 GitHub 任务发 INCIDENT，包括停在"待你审核""待你批准方案"、跟这次读取毫无关系的任务。一次网络抖动就把整个队列变成异常，用户得逐个 reconcile。
- 改：列表读取失败只记一条系统级日志或告警，不改变任何任务的状态；只有**跟某个任务直接相关**的外部读取（它的 CI、它的 PR）失败，才对这个任务发异常。

### K4（低）源码里的乱码
- `src/tandem/shell/store.py:192`：`ConflictError("GitHub ??? PR ?????????")`，中文在写入时丢了。改回正常中文，并检查别处没有同样的问题。

### K5（低）Issue 一律按 C 级提交
- `poll()` 用 `Level.C` 提交。按 ADR，等级以真实改动为准，交回代码后内核会重新计算，所以不算漏洞；但一个明显要动 `risk.yml` 的 Issue 会先当 C 级开工，没有先批方案。M1 可以接受，请在 `docs/github-adapter.md` 里写明这一点。
