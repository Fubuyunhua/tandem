# task-001 第一轮修改清单

两家审核的原文：`docs/tasks/reviews/task-001-codex.md`、`docs/tasks/reviews/task-001-claude.md`。下面是合并后的清单，按优先级排列。每一条都要**先写一个能复现问题的测试，确认它失败，再修代码**。

## 必须修
| # | 来源 | 问题 | 要求 |
|---|---|---|---|
| F1 | Claude 1 | 等级是按 Agent 回执里自己报的 `changes` 算的 | 回执里的 `changes` 字段一律忽略（记一条警告）。外壳新增"改动采集器"接口 `DiffSource`，根据 `base...sha` 自己算出 `ChangeSet`。真实实现用 `git diff --name-status -M`，再统计断言数量的变化；密钥扫描先留一个接口，默认"未扫描"，并在记录里标明。测试和 demo 用假实现。`CODE_SUBMITTED` 里的改动只能来自采集器 |
| F2 | Codex 1 | 改审核标准以后，可以绕过红色 CI 直接合并 | 把"当前提交编号的 CI 是绿的"作为**所有**产生 `MERGE` 动作的路径都必须满足的不变量，统一在一个地方检查。补回归测试：R01 之后改标准、两家都通过，仍然不能合并 |
| F3 | Codex 2 | 同一个提供方换两个审核者名字，就能冒充两家 | 审核结论按**提供方**去重，并且绑定指定的审核席位。放行前再核对一次：至少 N 家不同的提供方，而且都没参与过编写。补反例测试 |
| F4 | Codex 3 + Claude 3 | 审核期间来了新提交会被忽略；批准和合并没有核对提交编号 | 在所有允许接收新代码的非终点状态下，新提交都要更新提交编号，作废旧的审核、批准和否决，然后回到验收（必要时先回到方案批准）。`YOUR_APPROVAL`、`INTERVENTION_APPROVED`、`MERGED`、`CI_RED` 都**必须**带提交编号，并且和当前的一致；缺失或不一致就忽略。CLI 的 `approve` 增加必填参数 `--sha` |
| F5 | Codex 4 | 你自己提交代码时不重新算等级，也不记录参与过的 AI | 人工提交和 Agent 提交走同一套逻辑：按真实改动重新算等级，作废旧证据。事件里带上参与过的提供方，累加进 `providers_involved` |
| F6 | Codex 5 | "纯文档"只看目录，`docs/run.py` 也能降到 B；路径没有规范化 | 可放宽只认文档类型（比如 `.md`、`.txt`、`.rst`），并且在 `risk.yml` 里配置。路径先规范化：绝对路径、空路径、包含 `..` 的路径一律拒绝，直接按 D 处理。补测试 |
| F7 | Codex 6 | 事件、任务、动作不是原子保存；状态版本号挡不住并发覆盖 | 用一个事务保存"事件 + 带预期旧版本号的任务更新 + 待执行动作"，用 `UPDATE ... WHERE state_version = ?` 实现，并检查受影响的行数。事务提交以后再执行副作用。同一版本号只接受内容完全相同的重复保存。补并发冲突和中途出错的测试 |
| F8 | Codex 7 | `tandem approve` 在"待你审核"时发错了事件，状态不动 | "待你审核"发 `YOUR_APPROVAL`，"待你介入"发 `INTERVENTION_APPROVED`。事件被内核忽略时，CLI 返回非零，并打印原因。补单 Agent C 级、D 级批准的 CLI 测试 |
| F9 | Codex 8 | 审核过程中审核者失效时，第 16 条没有实现；`row_16` 的测试其实没测到这一条 | 待 AI 审核期间，如果收到审核者额度用完之类的事件，就按当前额度和参与历史重新检查，凑不齐时以 R03 进入"待你介入"。重写 `row_16` 的测试 |
| F10 | Codex 12 + Claude 2 | `risk.yml` 默认是多 Agent 模式；demo 不检查最终状态，失败了也返回 0 | `risk.yml` 默认改为 `single_agent`。demo 的场景 1 在代码里显式使用多 Agent 策略。每个场景都核对最终状态和提交编号，不符合就返回非零 |
