## 1. 一句话

做一个调度多家 AI 的开发循环系统：AI 承担大部分实现工作，系统本身保证你在使用过程中持续锻炼**数学建模、架构设计、批判能力**。

这个系统是你的第一个项目，从第一天起就**用它自己的流程开发它自己**。

## 2. 问题陈述

AI 产出的速度远超你理解、审核和学习的速度，由此带来三个后果：

- **审不过来**：没法逐一审核，又不敢全部放手。
- **看不懂**：项目在推进，你的理解没有跟上。
- **能力退化**：自动化越顺畅，你就越少思考、越少动手。

现有方案（agent-autoloop、Claude Code `/goal` `/loop`、Ralph loop）解决了第 1 点，但对第 2、3 点只有警告，没有机制。

## 3. 目标与非目标

**目标**
- G1 自动化：实现功能、修 bug、按规则自动审批。
- G2 成长：三项核心能力在项目过程中得到刻意练习，并且可以量化。
- G3 多 Agent：Claude / Codex / pi / agy 可以组合、可以替换，写代码和审代码由不同 Agent 完成，按额度调度。

**非目标（v1 不做）**
- 不自己实现 Agent 内循环，直接使用各家现成的。
- 不做生活场景的自动化。
- 不做无人值守的从零生成项目（Ralph 式）。
- 不做多用户。使用者只有你一个人。

## 3.5 分工

| | AI 负责 | 你负责 |
|---|---|---|
| 代码 | 大部分实现、接口对接、测试、修 bug | 模型的核心函数、接口定义 |
| 决策 | 提出备选方案、挑毛病、做 spike | 写下倾向和理由（ADR），并拍板 |
| 审查 | 多家审核（审核者不能是写过这次代码的模型提供方） | D 级和被抽中的 C 级：先独立 review，再和 AI 的意见对照 |
| 日常 | 依赖升级、巡检、盯 CI | 在手机上回答选项题，每天集中审阅一次 |

原则：
- 低风险的事 AI 自动完成，高风险和核心的事必须经过你。
- 风险高低由规则判断，不由 AI 自己判断。
- 规则在 GitHub 上执行，AI 无法绕过。

## 4. 三项核心能力 → 项目里的练习位置

> **所有权划分**（架构上叫"函数式内核 + 命令式外壳"）：
> - **纯计算的内核由你负责**：模型、决策规则、调度算法。这些都是纯函数，没有 IO，方便测试，也方便你推导。AI 也可以改内核，但 AI 改的要你批准（见 ADR-0001 的 `core/` 审核规则）。
> - **有副作用的外壳交给 AI**：接 GitHub、飞书、Agent 进程、存储。
>
> agent-autoloop 的内核也是纯函数（有测试强制保证没有 IO、没有时钟、没有随机数），可以作为参考。

### 4.1 数学建模（你来建模，并亲手写核心函数）
本项目里有四个真实的建模问题：

| 编号 | 问题 | 模型方向（你来决定，AI 只出备选方案） |
|---|---|---|
| MOD-1 | **信任校准**：某个 Agent 在某类任务上有多可靠，什么时候可以放权、什么时候要收回 | 用抽查结果做 Beta 后验，按置信下界决定升级或降级 |
| MOD-2 | **额度调度**：多份订阅，各有 5 小时窗口和周上限，任务该派给谁、什么时候跑 | 带约束的调度或优化问题，需要给交互使用预留额度 |
| MOD-3 | **注意力预算**：卡片到达的速率和你的处理能力之间怎么平衡，什么时候推送、什么时候合并成批 | 排队模型；在打断次数和等待延迟之间权衡 |
| MOD-4 | **抽查率**：B 级事项抽查多少，才能以给定置信度发现缺陷率超过阈值 | 抽样统计 |

练习形式：
1. 你先写建模文档：变量、假设、目标、约束。
2. AI 批评这份文档，并给出备选模型。
3. 你亲手实现核心函数。
4. AI 补测试、接线。
5. 上线后用真实数据检验模型的预测是否成立。

### 4.2 架构设计（你来决策，AI 出方案并批评）
- 每个架构决策都写一份 ADR，**由你执笔**。
- ADR 的流程：
  1. AI 先列出备选方案；
  2. **你写下自己的倾向和理由**；
  3. 再让另一家 Agent 来挑刺；
  4. 分歧大的地方先做 spike，用实际结果来定。
- 模块之间的接口定义（类型和协议）由你写，具体实现交给 AI。
- agent-autoloop 作为参考设计。每个 ADR 都要回答一个问题：它当时为什么这样做，我为什么相同或不同。

### 4.3 批判能力（你作为审查者，并有可度量的对照）
- **评审对照**：每个 D 级 PR 和被抽中的 C 级 PR，你先独立 review，写下发现的问题，然后再看审查 Agent 的意见。系统记录双方各自发现了什么、各自漏掉了什么。
- **否决记录**：你否决 AI 审核意见时逐条写理由，事后统计是你对还是 AI 对。
- **方案批判**：AI 给出的设计方案，你必须先写出至少 3 条批评，之后才能看 AI 的自我批评。
- **事实核查**：凡是调研类产出，你要抽查其中标注【未核实】和未标注的说法。这次调研中发现 agy 有多处错误，就是一个实例。
- **找茬练习**（仅限练习模式）：系统从历史 PR 里构造带已知缺陷的练习题。**真实 PR 里绝不注入缺陷。**

### 4.4 手写代码的定位
手写代码不再作为单独的目标，只保留在服务上面三项能力的地方：
- 建模用的核心函数；
- 接口定义；
- spike 中你想亲自验证的部分。

## 5. 功能需求

### F1 循环（四种）
| 循环 | 本项目里的用途 | 学习分量 |
|---|---|---|
| 回合式（herdr 交互） | 新模块、ADR、建模 | 重 |
| 目标式 | 修 bug、让测试变绿，完成条件以外部 CI 结果为准 | 中：失败测试由你来写 |
| 定时式 | 盯 PR 和 CI、处理 review 评论 | 轻：每周摘要 |
| 主动式 | 依赖升级、巡检 | 无：只做抽查审计 |

### F2 规则与分级
- `risk.yml` 定义"路径和动作"到"A/B/C/D 级"的映射，取所有匹配项中的最高级。
- 另外设两类特殊路径：
  - `core:`：内核目录，属于 D 级。你和 AI 都可以改：AI 改的要你批准，你改的要经过 AI 审核（你保留最终决定权）；
  - `decisions:`：关键决策，需要 ADR。

### F3 闸门（GitHub 侧）
- 机器人账号，只开最小权限，不授予 Workflows 权限。
- 分支保护。
- 必需检查：`risk-level`、`core-guard`、`size-limit`（≤300 行）、测试。
  - `comprehension` 从必需检查里移除（ADR-0001 终审第 12 条），改为 M4 阶段的异步理解抽查，**不阻挡合并**。C 级的理解抽查是每天固定 1 个。

### F4 回执协议
采用统一格式：第一行写结论，后面附 JSON。字段包括：
- **必填**：任务编号、第几次尝试、提交编号（ADR-0001 终审第 8 条；状态流转要用这三项做核对）；
- 沿用 agent-autoloop 的 `ask`、`notice`、`later`；
- 新增 `brief`，包含 what / why / verify / rollback / learn / level 六项。

### F5 人机接口
- **手机**：飞书卡片，只发选项题；每天最多 8 张，另有 2 次摘要；23:00–08:00 静默；如果没有回应，按安全选项处理。
- **桌面**：审阅队列和学习型决策卡，卡片附入门材料，并留有"先写你的猜测"一栏。

### F6 调度
- Agent 适配器接口：`command()` 和 `read()`，参考 autoloop 的设计。
- 写和审由不同的**模型提供方**负责；C 级要多家审核都通过。
- 额度计量。调度器暂缓（ADR-0001），M1 只记录每个任务实际消耗的额度，M3 再按 MOD-2 的结果调度。

### F7 记录与指标
- 只追加的事件日志，可以对任意一个 PR 追问"为什么是这个结果"。
- 理解债账本：记录你标注为"说不清"的模块。
- 每周报告，内容见第 6 节。

## 6. 成功标准（3 个月，到 2027-02 初）

| 维度 | 指标 | 目标值（初稿，可调） |
|---|---|---|
| 自动化 | 无需你介入就完成的任务占比 | ≥ 50% |
| 自动化 | 每天被打断次数 | ≤ 8 |
| 自动化 | 漏检（合并后才发现的缺陷） | 每月 ≤ 2，且每次都触发降级 |
| 建模 | 由你建模并上线的模型数 | ≥ 3 个（MOD-1 到 MOD-4 中任选） |
| 建模 | 模型预测与实际的偏差 | 有记录，并且在下降 |
| 架构 | 由你执笔的 ADR 数 | ≥ 8 篇 |
| 架构 | ADR 中"重新考虑的信号"实际触发后的复盘 | 每次触发都有复盘 |
| 批判 | 评审对照中你的发现率（你独立发现的有效问题 ÷ 双方发现的有效问题，去重后） | 有记录，并且在上升 |
| 理解 | 随机抽一个模块，你能讲清楚 | ≥ 80% |
