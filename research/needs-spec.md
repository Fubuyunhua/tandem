# 个人 AI 自动化流程 · 需求规格 v0.1

> 依据：`REPORT.md`（A/B/C/D 分级、理解闸门、审阅容量）、`agent-autoloop-analysis.md`（事件 → 规则 → 一轮 → 回执 → 卡片 → 续接 → 留痕）。
> 标【未核实】的条目需要你或我后续验证，不能直接当事实用。

## 0. 你已经定下的 5 个前提

| # | 决定 | 对设计的直接影响 |
|---|---|---|
| 1 | 先做代码 | 事件源只接 GitHub（Issue / PR / CI）+ 定时巡检；生活场景放到最后一个阶段 |
| 2 | 保持**核心逻辑**的手写能力 | 核心路径对 Agent 设硬性写保护；核心任务默认派给你，AI 只出测试和提示 |
| 3 | 手机随时拍板 | 卡片必须 30 秒内能决定；**看代码的审阅不能在手机上做**，要排队到桌面 |
| 4 | 用订阅，不用 API Key | 约束从"花多少钱"变成"额度够不够"；后台不能把你白天交互用的额度吃光 |
| 5 | 接受后台常驻 | 系统由事件驱动；需要解决常驻放在哪、怎么隔离、电脑睡眠怎么办 |

## 1. 总体架构：GitHub 是两个世界的边界

```
 手机（飞书卡片 / GitHub App）         ← 拍板：选项题，30 秒
        ▲
        │ 卡片 / 回答
 ┌──────┴──────────── WSL2 后台 ─────────────┐
 │ hub 常驻：轮询事件 → 规则路由 → 起 Agent 跑一轮 │
 │ claude -p / codex exec，各自独立 clone + worktree │
 │ 只推 agent/* 分支，开 PR，不能合并到 main        │
 └──────┬──────────────────────────────────────┘
        │ push / PR
 ┌──────▼──────── GitHub（硬闸门所在地）────────┐
 │ 分支保护 · CODEOWNERS · 必需检查 · risk 计算   │
 │ PR 体积上限 · 理解闸门检查 · 机器人账号权限      │
 └──────▲──────────────────────────────────────┘
        │ pull / review / 手写提交
 Windows 桌面（herdr 交互会话 · 审阅时段 · 手写练习）
```

**关键设计原则：硬闸门放在 GitHub，不放在 Agent 运行时里。**
- autoloop 的教训是：`askFirst` 只是提示词，真正的边界是权限。
- 只要闸门在 GitHub 服务端，编排器（autoloop 或自建 hub）用哪个、Agent 用哪家都无所谓，换掉也不影响安全性。
- 后台 Agent 只能开 PR，合不合并永远由 GitHub 规则和你决定。

## 2. 需求清单（按 autoloop 的环节）

### R1 事件源（代码阶段）
| 来源 | 触发 | 默认级别 |
|---|---|---|
| Issue 打上 `agent` 标签 | 你写的任务卡（手机上也能建） | 按任务卡里的风险字段 + 路径计算 |
| 你在 agent PR 上的 review 评论 | 续接原会话，按评论修改 | 沿用原 PR 级别 |
| CI 在 agent 分支失败 | 修复一轮，最多 2 次，之后转卡片 | 同原 PR |
| CI 在 main 失败 | 先诊断，只出报告 + 修复 PR | C |
| 每晚巡检 | 依赖 / 安全公告 / 死代码 / TODO | 产出 PR 均为 C |
| 每周日 | 理解债报告 + 周指标 | 通知 |

- **轮询，不用 Webhook**：hub 用 `gh` 定时拉取，家里电脑不需要公网入口。
- **任务卡是 Issue 表单**，必填：目标、非目标、验收标准、是否涉及核心、谁写（AI / 我 / 结对）。
- **创造型工作不进后台**：没有验收标准的 Issue，hub 只回一张卡"请先补验收标准"，不开工。

### R2 风险分级（硬规则，写在仓库里）
- 每个仓库有一份 `.agent/risk.yml`：路径 glob → 级别，外加动作类型（删除、迁移、发布、改 CI）。
- **CI 根据实际 diff 计算级别**，取所有命中规则里的最高级（rules + max），然后打标签。
- Agent 在回执里自报级别。自报和 CI 计算不一致时，以较高的为准，并记一笔"自评偏差"，用于判断这个 Agent 还能不能信。

| 级别 | 代码场景 | 谁放行 | 在哪放行 |
|---|---|---|---|
| A 自动 | 文档错字、格式化、lint 修复（**起步时为空，靠记录挣来**） | CI 绿灯自动合并 | — |
| B 做完报告 | 非核心、≤50 行、有测试覆盖的小修 | 你事后抽查 | 每日摘要 |
| C 你批准 | 非核心功能、依赖升级、配置 | 你 approve | ≤50 行可手机，否则桌面 |
| D 你决定 / 你写 | **核心逻辑**、鉴权与安全、数据迁移与删除、`.github/`、密钥、发布 | 你写或你逐行审 | 只能桌面 |

### R3 核心逻辑的手写保护（对应前提 2）
这是 autoloop 完全没有、而你最需要的部分。

- **核心路径由你列出**，写进 `risk.yml` 的 `core:` 段和 `CODEOWNERS`。
- **三道防线**：
  1. **GitHub**：agent 分支的 PR 只要碰到核心路径，必需检查 `core-guard` 就失败。只有你手动加上 `core-ai-ok` 标签才放行。
  2. **Claude Code 本地**：用 PreToolUse hook 拦截对核心路径的 Edit / Write，交互会话里也生效。
  3. **Codex**：没有对应的路径级 hook【未核实】，所以只依赖第 1 道防线。
- **核心任务的三种模式**（写在任务卡的"谁写"字段里）：
  - **我写**（默认）：AI 只有读权限，充当教练，只给提示不给答案。
  - **结对**：AI 先写测试（测试放在非核心目录），你写实现直到测试变绿。你只需审测试，测试比实现短得多。
  - **AI 写**（例外）：需要 `core-ai-ok` 标签，并且必须通过理解闸门（见 R5）。
- **练习配额**：每周至少完成 1 个核心任务的手写；"AI 写"的例外占比是一项周指标，持续升高说明你在退化。

### R4 回执（四家 Agent 统一）
沿用 autoloop 的格式：第一行写结论，末尾附 JSON 代码块。在它的 `ask / notice / resolve / later` 之外，**新增 `brief` 字段，专门帮你理解**：

```json
{"brief": {
  "what": "改了什么，三句以内",
  "why": "为什么这样改，否掉了哪个备选方案",
  "verify": "怎么证明它是对的：哪些测试、跑了什么命令",
  "rollback": "怎么撤回",
  "learn": "你最值得弄懂的一点",
  "level": "自评级别和依据"
}}
```
- `brief` 写进 PR 描述，方便你在手机和桌面上读同一份材料。
- **"做完了"以外部证据为准**：hub 自己去查 CI 状态、文件是否存在、测试结果，不采信 Agent 的自述。agy 这次没按要求标【未核实】，就是"自述不可信"的现成例子。

### R5 理解闸门（防止"看不懂也点了通过"）
- C / D 级 PR 的模板里有一节 **"我的理解"**，由你在合并前用三句话填写。
- 必需检查 `comprehension` 在这一节为空时失败。它防不住你糊弄自己，但能防止你顺手误点。
- **PR 体积上限**：agent PR 的改动不超过 300 行（锁文件和生成文件除外），超过就 CI 失败，打回去拆分。按你每天约 450 行的深度审阅容量算，一天最多认真审一个半这样的 PR。
- **计划检查点**：超过 300 行的任务必须先出计划（只交一份 md 文件），你批准计划后再动手。这和 autoloop 的"先问再做"是同一个机制，只是用在设计阶段。

### R6 手机卡片（对应前提 3）
- **卡片只能问选项题**：标题一句话，正文三行以内，2–3 个选项，标出推荐项，并写明每个选项的后果和撤回成本。不出现代码、文件路径和状态码（与 autoloop 的要求一致）。
- **手机上能拍什么**：
  - D 类的方向性决定（选方案 A 还是 B）；
  - ≤50 行、非核心的 C 级 PR：卡片里附 GitHub 链接，在 GitHub App 上 approve。
- **手机上不能拍什么**：核心逻辑、`.github/`、迁移与删除、超过 50 行的改动。这类事项只发一条"已排队到桌面审阅"的通知。
- **防审批疲劳**：
  - 每天最多主动推送 8 张卡，超出的进入摘要；
  - 每天两次摘要（建议 12:00、21:00）；
  - 23:00–08:00 静默，只有阻塞中的 D 类事项才推送。
- **超时默认走安全选项**：卡片没人回答时，选"不做 / 继续等"，绝不默认放行。
- **通道安全**：拍板通道本身就是一个认证入口。
  - 卡片回答要校验发送者身份；
  - **合并动作永远在 GitHub 上完成**，因为那里有你的 2FA；飞书卡片只负责回答选项题。
- **通道选择**：推荐飞书机器人，它支持交互卡片、国内可用，autoloop 也已经有现成的飞书插件可以参考。备选是 ntfy 或 Telegram。
  - 飞书能否以长连接方式接收回答（不需要公网回调）【未核实】。

### R7 额度管理（对应前提 4）
- **主要风险**：后台把周额度吃光，你白天想交互时没得用。这次 codex 的周额度只剩 24%，就是一个前兆。
- **规则**：
  - 后台最多使用周额度的 X%（建议从 30% 起步，由你决定）；
  - 剩余额度低于阈值时，后台只做 D 类阻塞项和 CI 修复；
  - 大任务排到夜间执行，利用 5 小时窗口的重置。
- **怎么计量**：
  - `claude -p --output-format json` 会返回 usage 和估算费用；`codex exec --json` 会返回 token 数。hub 按任务累计。
  - 命中限流报错时，暂停到重置时间再继续。
  - 能否直接查询剩余额度【未核实】，所以先用"自己累计"作为替代。
- **Agent 分工**（只有能后台运行的才进 hub）：
  - Claude：写代码主力；
  - Codex：对固定 SHA 做只读审查（写和审分开，沿用 REPORT 的结论）；
  - pi、agy：是否支持后台运行【未核实】，先只在 herdr 里交互使用。
- **服务条款**：用个人订阅在自己的项目上跑自动化，目前看属于个人使用。但后台批量运行是否有额外限制【未核实】，上线前要查一遍当期条款。凭据只给自己的 hub 用，不对外代理。

### R8 后台常驻（对应前提 5）
- **建议放在 WSL2，不放在 Windows 原生**：
  - Claude Code 的沙箱支持 Linux 和 WSL2，不支持 Windows 原生【需复核】。后台 Agent 是无人值守的，隔离比方便更重要。
  - autoloop 和多数参考实现只支持 POSIX。
  - 后台 Agent 使用 WSL 内**单独的 clone**，和你在 Windows 上的工作副本互不干扰，两边只通过 GitHub 交换代码。这一点也正好是隔离。
- **要处理的问题**：
  - **开机自启**：用 Windows 任务计划在登录时启动 WSL，WSL 内用 systemd 管理 hub。WSL 在空闲时会不会自动关停、需要怎么保活【未核实】。
  - **电脑睡眠**：睡眠期间 hub 暂停，醒来后靠轮询补上漏掉的事件，所以只要轮询是幂等的就能接受。如果你希望夜间巡检照常进行，就要调整电源设置。
  - **登录过期**：claude 和 codex 需要在 WSL 里各登录一次。令牌过期时，hub 发一张"待你处理：重新登录"卡片（autoloop 已有这个模式）。
  - **重复执行安全**：hub 保证每件事至少执行一次，所以每轮开始时先核实当前状态（PR 是否已存在、分支是否已推送），再决定做不做。

### R9 GitHub 侧的硬闸门（整个系统的安全底座）
| 闸门 | 作用 | 要注意的问题 |
|---|---|---|
| **机器人账号** | Agent 用独立账号开 PR | **GitHub 不允许批准自己的 PR**：如果 Agent 用你的账号开 PR，你就无法 approve。所以必须单独开一个机器账号 |
| 细粒度令牌 | 机器人只有指定仓库的 contents 和 PR 写权限 | **不给 Workflows 权限**，这样它推不了 `.github/workflows` 的改动，也就没法关掉闸门 |
| 分支保护 / Rulesets | main 必须走 PR，必需检查全绿，核心路径需要 CODEOWNERS 批准 | **私有仓库在免费版上用不了分支保护**，需要 GitHub Pro。也可以退一步，由 hub 在合并前本地检查，但那就是软闸门 |
| 必需检查 | `risk-level`、`core-guard`、`size-limit`、`comprehension`、测试 | 检查脚本本身属于 `.github/`，是 D 级 |

### R10 留痕与指标
- 沿用 autoloop 的思路：所有记录只追加不修改，并能按任一 PR 或事件查出"谁、按哪条规则、凭什么放行"。
- **新增理解债账本**：你在审阅时可以给某个模块标上"说不清"，每周报告列出这些模块，作为手写练习的选题来源。
- **每周 7 个指标**：
  1. 漏检（合并后才发现的缺陷）
  2. 回滚次数
  3. 每天推送的卡片数
  4. 卡片的中位响应时间
  5. 每天深度审阅的行数与预算之比
  6. 核心逻辑手写占比
  7. 后台额度占比
- **降级规则**：某类事项出现一次漏检，就升高一级，持续 2 周。
- **升级规则**：连续 20 次抽查无问题，系统提议降一级。是否采纳由你批准，这就是"自适应放权"。

## 3. 分阶段落地

| 阶段 | 时间 | 做什么 | 不做什么 |
|---|---|---|---|
| **0 立规矩** | 第 1 周 | 选 1 个仓库，列出核心路径，写 `risk.yml`、PR 模板、4 个必需检查，建机器人账号，开分支保护。继续用 herdr 手动派活。开始每周一个核心手写任务 | 不上后台 |
| **1 最小循环** | 第 2–3 周 | 在 WSL 起 hub，只接一个事件源（`agent` 标签的 Issue），只用 claude，只产出 C/D 级 PR，飞书卡片 + 每日摘要 | 不自动合并 |
| **2 扩展** | 第 4–6 周 | 加入 CI 失败事件源、Codex 审查、每晚巡检、额度计量；给记录干净的类别开放 B 级 | A 级仍然为空 |
| **3 放权与学习** | 第 7 周起 | 从你的决定中提议规则，开放少量 A 级，接入理解债账本 | — |
| **4 生活** | 代码稳定后 | 复用同一套框架，邮件和支付类一律按 D 级或草稿模式处理（防"致命三角"） | — |

**编排器的选择推迟到阶段 1 再做**：因为闸门都在 GitHub 上，编排器是可以替换的。
- 选项一：在 WSL 里直接用 autoloop 当编排器。它的内核（事件溯源、续接、卡片、飞书）很扎实，省去自己写的工作量。
- 选项二：自建一个轻量 hub，只借用它的回执协议和日志设计。
- 阶段 1 开始前，用 R1–R10 逐条对照 autoloop 能否满足，再决定。
