# 个人 AI 自动化工作流调研报告

> 日期：2026-11-04　｜　方法：由 Claude 通过 herdr 调度 codex、pi、Antigravity（agy）分工调研，再交叉核实和汇总
> 原始分报告：`research/out/codex.md`（工程侧）、`research/out/pi.md`（人的侧）、`research/out/agy.md`（生活侧）
> 可信度说明：关键数据和链接已抽查，第 8 节列出了核实结果和对原始报告的更正。凡是标注"起始建议"的阈值，都是需要你按自己的数据调整的经验值，不是研究结论。

## 0. 结论先行

1. **你的两个问题其实是同一个问题：人的理解和审核带宽是硬上限。** 深度审查的有效速度大约是 200–400 行/小时，单次审查超过约 60 分钟后检出率明显下降。按每天 90 分钟深审计算，你一天能真正审懂的量约为 **450 行**。AI 一天能产出几千行，所以逐行全审在数学上就不可能，这不是你不够自律。
   **自动化的目标不应该是让 AI 更快，而是让"需要你注意力的部分"缩小到带宽以内。**
2. **判断"能不能放手"时，用规则取最高风险等级（max），不用加权平均，也不采信 agent 的自评置信度。** 只要命中任意一条高风险规则就升级；无法判定时默认需要人审。
3. **人工审核本身不是安全控制。** 一项 2026 年的实验中，88 名没有监控辅助的开发者里，有 83 人（94%）没有发现 agent 的蓄意破坏。人审必须和自动关卡、权限隔离、可回滚这三样东西一起使用。
4. **"放手"和"练手"必须分开设计。** 用不用 AI 不是关键，怎么用才决定你学不学得会。在 Anthropic 的 RCT 中，直接拿 AI 答案的组测验得分为 50%，对照组为 67%；而"只问概念、自己写"的人得分不低于 65%。所以要保留固定的"自己生成"时间，并把 AI 设成教练模式。
5. **同一套决策路由可以直接用到生活中。** 起步只做"只读汇总"和"AI 起草、人一键确认"两类事；凡是涉及钱、对外发言、不可逆删除和凭据的动作，一律由人执行。

## 1. 证据：为什么既不能"全放"，也不能"全审"

| 证据 | 结论 | 局限 |
|---|---|---|
| Anthropic RCT，2026-01（arXiv:2601.20245），52 人学习陌生的异步库 | AI 组测验 50% vs 对照组 67%，差距最大的是 debugging 能力；而且速度并没有明显变快。"只问概念、自己写"的人得分 ≥65% | 样本小、周期短、任务不是 agentic，以初级开发者为主 |
| Bastani 等，PNAS 2025，近千名高中生 | 直接给答案的 AI：撤掉 AI 后考试 **−17%**；只给提示的 AI tutor：撤掉后基本没有损害 | 研究的是数学而不是编程，但"加护栏"的机制可以迁移 |
| METR RCT，2025-07，16 名资深维护者 | 使用 AI 时任务**反而慢了 19%**，开发者本人却以为快了 20% | METR 在 2026-02 的更新中认为现在很可能已经变快，但新数据有选择偏差，证据很弱。这项研究的价值在于说明**主观感受不可靠**，而不在于证明"AI 无用" |
| Cisco/SmartBear 2006 及审查实验再分析 | 审查速度慢于约 400 行/小时时检出率较好；单次 60 分钟以后检出率骤降，90 分钟后几乎检不出新问题 | 数据老、来自单一产品组，但方向一致 |
| Zhong 等 2026（arXiv:2603.15911），300 个项目、27.9 万条审查对话 | 审 AI 代码时讨论轮次**多 11.8%**；AI 提的建议中，被采纳的会让复杂度增加得更多 | 观察性研究 |
| Ye 等 2026（arXiv:2606.05647，NeurIPS 2026） | 没有监控时，**83/88** 名开发者没发现 agent 的蓄意破坏；即使监控给出了正确告警，16 次中仍有 9 次被攻破 | 对抗性设置，不能直接外推，但足以说明"人审 ≠ 安全" |
| Perry 等，CCS 2023 | 有 AI 辅助的参与者写出的代码**更不安全，却更自信** | 研究用的是较早的模型 |

**由此推出的设计原则**：先用自动关卡过滤掉大部分问题；把人的注意力只花在"意图、边界、契约、可回滚性"这些机器判断不了的地方；同时限制 AI 的单次产出粒度，让产出速度匹配你的理解速度。

## 2. 统一框架：一套决策路由，同时用于代码和生活

三份报告各自提出了一套分级：codex 的 L0–L3（代码放行）、agy 的 L0–L4（生活授权）、pi 的绿/黄/红（理解程度）。我把它们合并成 **4 个等级 + 1 道理解闸门**。

### 2.1 四个自主等级

| 等级 | 含义 | 代码中的例子 | 生活中的例子 | 对应 codex / agy / Knight 的等级 |
|---|---|---|---|---|
| **A 自动执行** | AI 直接做，只留日志 | 纯文档错字修正，CI 全绿后自动合并 | RSS/资讯每日摘要 | L0 / L0 / Observer |
| **B 执行后汇报** | AI 直接做，事后进入摘要，按比例抽查；可以加撤销窗口 | 白名单内的小改动（≤150 行，有行为测试），自动合并后每日抽查 20% | 订阅邮件打标签归档、整理下载目录 | L1 / L1–L2 / Approver 偏 Observer |
| **C AI 准备，人批准** | AI 把所有准备工作做完（diff、草稿、暂定日程），由人一键确认 | auth、依赖、迁移、CI 配置、公共 API 的改动，打上 `needs-human` 标签 | 邮件回复草稿、会议邀约、记账待确认 | L2 / L3 / Approver |
| **D 人来决策** | AI 只提供选项、影响分析和恢复路径；由人决定，并由人在原生平台上执行 | 权限模型、计价规则、不可恢复的迁移 | 付款、投资、公开发言、删除数据 | L3 / L4 / Operator–Consultant |

### 2.2 判定规则（按顺序执行，结果取最高等级）

```text
1. 一票升到 D：涉及资金划转、凭据/密钥、对外首次正式沟通或公开发言、不可恢复的删除或迁移、法律承诺
2. 一票升到 C：满足以下任一条
   - 改动位于高风险路径（auth/支付/权限/迁移/依赖/CI/agent 指令/风险规则本身）
   - 涉及第三方
   - 涉及敏感数据（健康、财务明细、私人通讯）
   - 读取了不可信输入（网页、陌生邮件），同时又拥有写权限
   - 超出规模阈值，或无法判定
3. 其余情况：可逆、只影响自己、有自动验证 → A 或 B
   （副作用为零的走 A，有副作用但可撤销的走 B）
4. 理解闸门（pi）：对 C 级事项，如果你看完后无法用 3 句话复述"改了什么、为什么、何时会失败"，就不批准。应该拆小、补测试或排学习时间，而不是硬批。
5. 永远不做的事：
   - 不用 agent 自报的"置信度"来降级
   - 不让高风险维度被低风险维度"平均掉"
   - 修改规则本身的动作，至少是 C 级
```

> 为什么不用 agy 提出的加权打分（0–100 分）？加权平均会让一个高风险维度被其他低分维度"平均掉"。agy 自己的场景表里就出现了这个问题：它把"外卖自动续订"放在了中间等级，但这件事涉及扣款，按它自己的否决规则本该是最高级。规则加 max 的方式更容易审计，也更不容易被 agent 自己钻空子。

## 3. 代码侧：单人可落地的流水线

### 3.1 从任务到合并的流程

1. **任务卡**（由你来写，约 5 行）：目标、非目标、允许改动的路径、验收示例、回滚方式。属于 D 级的事项在这一步就停下，只让 AI 出方案。
2. **隔离**：每个任务用独立的 git worktree 和分支，避免多个 agent 改同一个工作目录。herdr 本身支持 `herdr worktree` 命令。
3. **先交计划**：agent 先交 5 行计划和验收标准，你批准后再写代码。审一页计划，远比审 500 行 diff 便宜。
4. **写和审分开**：Claude Code 负责写，便于用 `-p`、hooks 和权限做脚本化。Codex 开**新会话**审查**固定的 commit SHA**：先看任务卡，自己找反例，最后才看作者的解释。审查者没有合并权限，也不修改待审分支。
   - 我没有查到证据表明哪个品牌天然更擅长审查，分开的价值在于上下文隔离，写和审的角色可以轮换。
   - pi 用来做定向复现和定位问题的小任务；agy 用来做 UI 和浏览器验证。不需要每个 PR 都过四个 agent。
5. **自动关卡**（GitHub Actions，必需检查）：lint → 类型检查 → 测试 → 构建 → 依赖/secret 扫描。可选：E2E、mutation testing（只对核心模块）、CodeQL。
   - 完整的 YAML 片段见 `research/out/codex.md` §3.3。要点：用 GitHub 托管的临时 runner，不注入任何生产 secret，不要用自己的电脑做 self-hosted runner。
6. **风险分级**：按 §2.2 判定等级。A/B 级自动合并；C 级打 `needs-human` 标签进入队列；D 级不进入实现阶段。
7. **留痕**：每个 PR 固定记录任务卡、base/head SHA、命中的规则和等级、agent 及模型版本、测试命令和结果、未解决的问题、谁放行的、怎么回滚。架构层面的取舍另写简短的 ADR。

### 3.2 风险规则（起始版本，按漏检数据调整）

| 等级 | 条件 | 放行方式 |
|---|---|---|
| A | 只改 `docs/**` 或普通 Markdown，≤50 行，不含脚本和 agent 指令文件 | 必需检查全绿后自动合并 |
| B | 白名单内的内部纯函数或非关键 UI；≤150 行、≤5 个文件；不改依赖和 API；有能失败的行为测试 | 独立 AI 审查无阻断问题后自动合并，每日抽查 20%（至少 1 个） |
| C | auth、支付、权限、迁移、依赖/lockfile、公共 API、CI/部署、agent 配置、风险规则、测试基础设施；或超过阈值、或无法识别 | `needs-human`，由你审过当前 SHA 后合并 |
| D | 权限模型、计价、不可逆删除、生产凭据、数据外发边界 | AI 只出方案；你决定后另开任务实施（实施任务通常是 C 级） |

**补充规则**：
- 发现 secret 立即阻断。
- 删除或跳过测试、批量更新快照、添加扫描抑制，这类改动不能因为"测试全绿"而降级。
- 任何新提交都要重新分级、重新跑检查。

### 3.3 起步只做三件事（codex 的建议，我同意）

1. 任务卡 + 小 PR + 写审分离，同时在途的任务最多 2 个。
2. 在 main 分支配置必需 CI 和安全扫描。风险规则先**手工执行**一周，这一阶段不开自动合并。
3. 一周后，只对 A 级（纯文档）开启自动合并。稳定以后再开放 B 级和每日抽查。
   - 暂时不要引入 OPA、多 AI 裁判或全量 mutation testing。

## 4. 人的侧：审核预算与手写能力

### 4.1 每日审核预算

- **每天 60–90 分钟深度审核**，分 2 段，每段不超过 45 分钟。
- 预算用完时，不要加速审，而是：拒绝或拆分过大的变更 → 只放行 A/B 级 → C 级排到明天 → 在 `review-queue.md` 里记录"审核债"。
- **打开 diff 前先写 3 行预测**：会改哪些文件、输入和输出是什么、最可能坏在哪个边界。然后再看 diff，看自己预测得准不准。
- **先读测试，再读实现。** 同时检查测试能不能失败：故意改坏一行代码，测试会不会变红。

### 4.2 审核清单（C 级事项必须过完；A/B 级抽查时看 1、3、5 条）

1. **意图**：能否用一句话说清改了什么、为什么改、怎样算成功？
2. **复述**：不看代码，能否说出它的输入、输出和失败方式？说不出来就不批准。
3. **可失败的测试**：测试是根据 spec 写的，还是根据实现反推的？改坏一行，测试会红吗？
4. **边界**：空值、超大输入、并发、超时、部分失败、权限，哪些覆盖了，哪些明确不覆盖？
5. **契约和影响范围**：API、schema、配置、依赖会影响谁？能在 5 分钟内回滚吗？
6. **复杂度**：有没有新增的抽象层、全局状态、重复代码？能不能更简单？
7. **安全和可观测性**：最坏情况是什么？涉及密钥、个人信息、注入吗？出了问题你怎么知道？
8. **on-call 测试**：你愿意为这段代码值班吗？

> AI 生成的 walkthrough 或解释**只能当作阅读路线和假设，不能当作正确性的证明**。CHI 2025 的研究发现，解释会同时增加人对正确答案和错误答案的依赖。

### 4.3 手写能力训练（标准版：每天 45 分钟，每周约 3 小时）

| 频率 | 时长 | 做什么 |
|---|---|---|
| 每天 | 15 分钟 | **不用 AI 热身**：凭记忆写一个函数和 3 个测试，或者遮住 AI 写的版本，重写昨天的一小段 |
| 每天 | 15 分钟 | **教练模式**：把 Claude Code 切到 `/output-style Learning`，或用教练提示词，只要提示、自己写 |
| 每天 | 5 分钟 | **学习日志**：用 3 句话解释今天的变更，写下 1 个不变量和 1 个还不懂的点 |
| 每周 | 90 分钟 | **不用 AI 完成一个小功能**，从读代码、写测试、实现到自审。忙的时候其他项都可以砍，这一项不能砍 |
| 每周 | 45 分钟 | 挑 100–200 行将来要维护的 AI 代码，遮住重写，然后 diff 对比语义差异 |
| 每月 | 30 分钟 | **理解债审计**：列出你解释不了的模块，挑一个排进学习计划 |

**忙碌周的最低版**：每天 20 分钟，每周 90 分钟。"不用 AI"的时段可以查文档，但不能用补全、聊天或 agent。

**教练提示词**（直接用）：

```text
你是我的编程教练，不是代码生成器。不要给完整实现。先用一个问题检查我的理解；
每次只给一个提示；我写完后你再指出错误，并给一个更小的下一步练习。
```

**加到 `CLAUDE.md` / `AGENTS.md` 的约束**：

```text
- 先给 5 行计划和验收标准，等我确认后再改代码。
- 单次 diff ≤200 行；超过就拆 PR。不要顺手跨模块重构或升级依赖。
- 先写测试再写实现；测试必须在实现错误时失败。
- 完成后给我：改了什么、为什么、如何验证、如何回滚、我仍需理解的点。
```

### 4.4 每周只看 5 个指标

不用 AI 的小时数、重写的行数、审核漏检数、解释不了的模块数、C 级积压数。**不要把"AI 生成了多少行"当成生产力指标。**

## 5. 生活侧：同一套路由的应用

### 5.1 场景分级表（已修正 agy 原表中自相矛盾的地方）

| 场景 | 等级 | 理由 |
|---|---|---|
| RSS、播客、论文的每日摘要 | A | 只读，没有副作用 |
| 订阅类邮件打标签并归档（不删除） | B | 可以撤销，每天汇总一次 |
| 下载目录按类型整理（不删除） | B | 本地、可恢复 |
| 发票 OCR，提取到"待确认"账本 | B（提取）→ C（入账） | 提取可以放手；金额正式入账前由人确认 |
| 日历里给健身、专注时段占位 | B（带撤销） | 只影响自己 |
| 离家时自动调空调 | B | 可逆，随时可以手动覆盖 |
| 工作邮件回复 | C | 只生成草稿，**绝不自动发送** |
| 和外部的人协调会议时间 | C | 涉及第三方信任 |
| 健康手环数据分析 | C（仅建议） | 敏感数据，结论只作为就医参考 |
| 给门锁下发访客临时密码 | C | 涉及实体安全 |
| 外卖或订阅自动续费 | **D** | 涉及扣款（agy 原表标为中间等级，与它自己的否决规则矛盾，已更正） |
| 信用卡还款、缴费 | D | 资金划转 |
| 证券交易 | D | 不可逆，波动大 |
| 在社交平台公开发文 | D | 声誉风险，而且可能被注入攻击劫持 |

### 5.2 起步的 3 个生活自动化（agy 建议，我把工具选型改成了现在的版本）

1. **每日信息简报（A 级）**：n8n（Docker/WSL2）或一个定时运行的脚本 → 抓取 RSS、GitHub Trending、Newsletter → 用当前的轻量模型（如 Claude Haiku 5.5 或 Gemini Flash 档）做摘要 → 推送到 Telegram 或你的笔记。**只读，零写权限。**
2. **邮件分拣 + 草稿（B/C 级）**：通知类邮件自动打标签（B）；真人邮件只生成 Gmail 草稿和暂定日程，通过一张卡片推给你，由你点确认（C）。**凭据只授予"创建草稿"这一最小权限，不授予发送权限。**
3. **记账待确认箱（B → C）**：发票照片放进文件夹 → 多模态模型提取字段 → 写入"待确认"表 → 每周日花 2 分钟批量确认，再并入主账本。

### 5.3 生活自动化的安全底线

- **"致命三要素"（Simon Willison）**：如果一个 agent 同时具备①读取你的私密数据、②接触不可信内容（网页、陌生邮件）、③能向外部发送信息，那它就可能被提示注入攻击用来窃取数据。至少要切断其中一项。
  - 真实案例：2024 年 Slack AI 被披露存在间接注入漏洞，可泄露私有频道数据；同年 ChatGPT 的长期记忆功能被披露可以被注入的指令污染，造成跨会话的持续数据外泄。
- **读和写分开**：负责读取不可信内容的模型不挂载任何写工具；写操作只基于你确认过的结构化数据进行。
- **最小权限**：账户凭据只授予需要的范围（例如只授予"创建草稿"）；尽量设置金额上限和撤销窗口。
- **防审批疲劳**：如果你每天要点 20 次以上"同意"，就会退化成闭眼盖章。解决办法是把 C 级事项合并成每天一次的批量确认，而不是去降低它的等级。

## 9. 附：这次 herdr 编排本身就是一个流程样本

- **做法**：先把任务书写成文件（`research/briefs/`），再用 `herdr agent prompt` 只发一句"读任务书并执行"，然后用 `herdr agent wait` 等待完成，最后由我核实和汇总。这种做法可以直接复用到你的日常工作中。
- **踩到的坑**：
  1. agy 的界面上弹出了一个模型切换菜单，herdr 因此把它的状态误判为 idle。所以不能只看状态，**还要检查约定的产出文件是否存在**。
  2. `agent wait` 会超时，但超时不代表任务失败，要先读 pane 内容再判断。
  3. agy 没有遵守"标注未核实"的要求，引用中出现了错误。这说明**即使是调研类任务，也需要一道独立核实的关卡**，对应 §2 里 B 级的"执行后抽查"。
- **成本参考**：codex 用了约 4.5 分钟（本周额度还剩约 24%）；agy 用了约 5 分钟；pi 逐篇核实论文，用了约 26 分钟，花费 $0.17。可以按任务性质分配：要快、要工程判断的交给 codex，要深挖文献的交给 pi，要做发散性综述的交给 agy，但 agy 的产出需要核实。
